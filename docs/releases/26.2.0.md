# Pawtropolis Tech 26.2.0

Released on 2026-11-15, the third release of that day. It brings the chat research pipeline back (decision 15 of the v26 audit, #00295): one job that scores the messages of the main chat on the host, and the Quality tab of the dashboard, which shows the scores to moderators and up. The bot's own code does not change.

This file describes the deploy as planned. The record of how it went follows once it has run. The full list of changes is in [`CHANGELOG.md`](../../CHANGELOG.md).

## The choices

You decided that the pipeline comes back and left its scope to me. The plan in #00295 had four open choices, and this release takes them like this:

- **Scores and the tab**, not scores alone.
- **With the embedding library on the host.** Without it only the rule-based score, the reply count and the older effort model are left. On its test set that model explains 32% of the variance of the labels, the embedding model 68%.
- **The whole channel since 2021-10-08**, not only the seven months of the first study.
- **The seven dead cron lines were stopped at once**, on 2026-11-15 at 14:52:59 UTC, before anything was built. They had done nothing but write the same error since May.

If you would have chosen differently, "Rolling back" below says how each part comes out again.

## What you will notice

**The dashboard has a Quality tab.** It is in the navigation for moderators and up, between Pulse and Heatmap. For a time window (7, 30 or 90 days, all time, or two dates) it shows five headline numbers, the last twelve weeks against the four before them, effort by week, the spread of the effort scores, ten weekly measures and three boards of authors. Each chart says under it what it measures. The line at the top says how many messages are scored and when the job last ran, and it turns into a warning when that is more than 45 minutes ago.

**The boards rate messages, not people.** The page says so above the boards. The effort score is the estimate of a small model that was trained in April on 2,774 messages which Claude Haiku had labeled once. Its mean error against those labels is 0.085, on a scale of 0 to 1. Read a board as a hint about where to look.

**One job in place of seven.** Cron starts it every 15 minutes. A run reads the last three days of the main chat from the message archive, scores what is new or edited, takes the score of a deleted message away, counts replies and rebuilds the weeks that changed. The first run after 09:00 UTC goes over the whole channel. No run has to be told what is left to do: after it, the score file says what the archive says.

**The bot's database stays as it is.** The first pipeline was taken out in May because the database had grown to 9.4 GB. It stored two vectors and a second copy of the text for every message. The new job stores results only, about 100 bytes a message, in `data/research.db`. The bot's database, its backups, its replication and its start check do not see that file, and the job opens the bot's database read-only.

**No message leaves the host.** The vectors are computed on the host's own CPU, with a model whose four files are pinned by their SHA-256. No outside service is called, the Claude API included: the labeling in April was a one-time step for training.

**The whole history is there from the start.** The 1,965,039 messages with text that members wrote since 2021-10-08 were scored on the dev machine, and the file was copied to the host. From there on the host scores about 1,000 new messages a day.

**The crontab is clean.** Seven lines of the first pipeline had run into a missing table every 15 to 60 minutes since 2026-05-15. They are gone, and the five empty tables they kept creating go with migration 086.

## What was measured

All of it on 2026-11-15.

**The history.** The dev machine scored 1,965,039 messages in 35 minutes, as ten parts of the channel with four processes at a time, one thread each. The parts were merged into one file of 200 MB (199,946,240 bytes, 102 bytes a score) with 5,888 authors and 267 weeks. The first pass over the merged file counted the replies of 630,220 messages and built the 267 weekly rows in 34 seconds.

**The first attempt at it used too much memory.** Ten processes at once took 23 GB on the dev machine. A batch of texts was limited by its count alone, and one very long message made its whole batch sixteen times as costly as a batch of short ones. A batch is now limited by what it costs. On 3,001 messages around the longest one of the main chat the process peaks at 392 MB where it took 2,026 MB before, and every score is the same.

**The two machines agree.** The host scored 1,200 messages that the dev machine had scored too. The effort scores differ by 0.00000018 at most, and the rule-based score and the filler flag differ in no row. So the series does not jump where the host takes over.

**The new scores against the first study's.** From the vectors the first study had stored, the new code gives back all 945,625 of its effort scores to the last digit, and the rule-based score of all 980,146 of its messages is identical. The vectors themselves cannot be made again: the first study used the 8-bit model, which gives one text a different vector depending on the other texts in its batch. The job uses the full-precision model, which does not. On 2,000 messages its effort scores differ from the stored ones by 0.013 on average.

**The job on the host**, tried in a scratch folder against a read-only view of the bot's database:

| Run                                                          | Time   | Peak memory |
| ------------------------------------------------------------ | ------ | ----------- |
| Nothing to score                                             | 0.4 s  | 79 MB       |
| One new message, which loads the model (one build earlier)   | 1.5 s  | 354 MB      |
| 600 messages with two threads                                | 10.9 s | 421 MB      |
| The daily pass over the whole channel, with 323 new messages | 26.2 s | 632 MB      |

The host has two CPUs and 6.2 GB of memory available. The daily pass took 33.3 s and 1,142 MB before it was changed to read the archive a day at a time.

**The tab's queries on the host.** The default window of 30 days reads its numbers in 65 ms. The all-time window takes about 4.1 s, on the dashboard's one thread, and the page keeps the answer for half an hour. That wait is #00297.

## How it goes out

1. CI on `release/v26.2`, then `main` is fast-forwarded to the branch. The push starts the dashboard workflow, which waits for CI on `main` and puts the new dashboard on the host.
2. Before that push, the score file of the history is copied to `data/research.db` on the host. The dashboard keeps the file open once it has read it, so the file is in its place first and is never swapped for another afterwards.
3. `./deploy.sh` with its database backup. It installs the library in `research/` (43 packages, 10 seconds in the trial), fetches the four model files (4 seconds), runs migration 086 and restarts the bot. No command is added, so Discord sees no change.
4. One run of the job by hand with `--full`, which scores what came in since the history was exported.
5. The crontab line, with the command in `scripts/quality-cron.txt`.
6. Checks: the bot and the dashboard at 26.2.0, the five tables gone and `user_names` as it was, a line of the job in `data/research.log` from cron, and the page's queries against the live file.

## Rolling back

**The tab.** It reads a file and writes nothing. To hide it, take the Quality entry out of `web/src/lib/components/layout/Nav.svelte` and push; the page then still answers by its address, for moderators and up.

**The job.** Remove its line from the crontab on the host:

```bash
ssh bash-ec2 'crontab -l | grep -v "dist/scripts/research.js" | crontab -'
```

Nothing else depends on it. The bot never imports the job's code, and the dashboard shows the scores it finds with a warning that the last run is long ago. To give the disk back as well, remove `data/research.db`, `data/research.log`, `data/research.lock`, `data/research-model` and `research/node_modules` on the host, 0.8 GB together.

**The release.** Check out `93aeb4b4`, the commit 26.1.0 was built from, and run `./deploy-no-tests.sh`. Remove the crontab line as above, because a deploy unpacks over the folder and leaves `dist/scripts/research.js` where it is. The database needs nothing: 26.1.0 never read the five tables.

**The five tables.** Nothing has to be restored. They were empty, and each of the first study's scoring scripts creates its table again when it runs.
