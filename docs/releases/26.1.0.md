# Pawtropolis Tech 26.1.0

Released on 2026-11-15. Production has run 26.1.0 since 2026-11-15 13:03 UTC, built from commit `93aeb4b4` of `release/v26.1`, and every Node app on the host has run on Node 24.22.3 since 13:16 UTC the same day. `main` was fast-forwarded to the branch before the deploy, once CI had passed on it.

This release carries out the decisions the owner took on 2026-11-15 about the questions 26.0.0 left open. The full list of changes is in [`CHANGELOG.md`](../../CHANGELOG.md), and the decisions are in [`MODERNIZATION_PLAN.md`](../../MODERNIZATION_PLAN.md), section 7.

## What you will notice

**Keys are set from Discord.** `/service-keys` is new and owner only. `status` shows which of the three services has a key (Google Vision, SauceNAO, e621) and what is lost without one. `set` opens a private form, tries the key against its service in one real request and stores it only when the service accepts it. `clear` removes a key, and `test` tries the stored ones again, for example after billing was switched on. A new key counts from the next scan or lookup on, without a restart. No reply and no log line shows a key. The status view does not say who set a key or when; that is in the bot log, as `service_key_set` and `service_key_cleared`.

**`/investigate-artist` also searches the open web.** Google's web detection is the fourth lookup, next to Fluffle, e621 and SauceNAO. It finds pages that hold the image or a part of it, which is where a picture taken from a shop listing, a portfolio site or a social feed turns up. It runs on the Google Vision key, so it is on whenever that key is stored, and `/service-keys clear` stops it together with the avatar scan. There is no separate switch. When it runs, the ticket's images go to Google.

**The report rates by the handbook.** Where the applicant-facing requirements and the mod handbook disagreed, the handbook decides: two of timelapse, layered source file and dated WIP photo are enough. The three six-month rules and work made on a base are in the handbook the way you settled them. The report no longer has the "Where the workflow is unclear" block. When the greeting in a ticket still carries the line about three sets of WIPs, the Notes say so, because the applicant was told it.

**One open ticket per type, once the bot's own tickets are live.** In the first-party ticket system, a member who already has an open ticket of a type gets a link to it from the open button, and no second ticket. That system is not live, Ticket Tool is, so nothing changes in the server today.

**`/purge` asks for a staff role first.** A caller without one is refused before the password is looked at.

**The log reads right again.** "User leveled up to 15" used to be written as a line of log level 15, and the error line for a level reward that could not be granted carried the member's level in place of the error level. Those lines have their real level now. The field is called `levelNumber`, and `alertLevel` in the disk space alert.

**The message archive writes about half as much.** Two of its three indexes were never read. Migration 085 drops them: 3.09 page writes for an archived message instead of 5.78, measured on a rebuilt copy of the table.

**The host runs Node 24.** Node 20 passed its end of life in April 2026. Every Node app on the host moved together, through apt, in the same maintenance window as this deploy. The bot was restarted three times in thirteen minutes for it, a few seconds each time.

## What is left for you

1. **Make Google accept the Vision key.** Google refuses the stored key with HTTP 403, in two wordings: "This API method requires billing to be enabled" and "Permission denied on the service" (reason `ACCESS_DENIED`). In the Google Cloud project behind the key, check that billing is on and that the Cloud Vision API is enabled, or make a new key. Then run `/service-keys test`, or `/service-keys set` for a new key. Until then the avatar scan, `/audit nsfw` and web detection do nothing.
2. **Create the SauceNAO and e621 accounts** and enter the keys with `/service-keys set`. Both are free. Without them those two lookups are skipped, and the report says so.
3. **Have staff edit the public requirements message and the ticket greeting.** They still ask for three sets of WIPs or layers. The handbook, which decides now, asks for two of three kinds of proof.
4. **Read the three new rule blocks in the mod handbook** (process evidence, the six-month rules, bases). They were written from your decisions and you may want other words. The criteria in `src/features/artistInvestigation/criteria.ts` quote those lines, and a test holds the two together, so a reworded line has to change in both places.
5. **Reboot the host when it suits you.** Ubuntu flags a reboot as required for an updated libc and a newer kernel. That is older than this release and no part of it. The PM2 unit, the other Node service, nginx and Litestream are all enabled at boot, and the list PM2 starts from was saved by this deploy.
6. **Clear out what the move left on the host**, once Node 24 has run for as long as you want to keep the way back. The directories are under "Left on the host" below.
7. **Carried over from 26.0.0:** run `/investigate-artist` once in a 2D artist ticket you know well, do one dashboard action that calls the bot, and run `/sync-tasks`.

## The three keys

| Key                          | On the host                         | Without it                                                                                 |
| ---------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------ |
| `GOOGLE_VISION_API_KEY`      | Set, and refused by Google with 403 | No avatar scan on join or avatar change, no `/audit nsfw`, no web detection in the report. |
| `SAUCENAO_API_KEY`           | Not set                             | The SauceNAO lookup is skipped.                                                            |
| `E621_LOGIN`, `E621_API_KEY` | Not set                             | The e621 lookup is skipped. Both values are needed.                                        |

The keys are lines in the host's `.env`, the same place `/config isitreal` writes to. The first plan was an encrypted database column. Its encryption key would have had to live in `.env` as well, so the secret would have depended on that file anyway and gained a second place to lose. The Claude API key is not one of the three; it stays a line you edit by hand.

Google bills web detection per image: 3.50 USD per 1000 images after the first 1000 in a month, by [Google's price list](https://cloud.google.com/vision/pricing) on 2026-11-15. A run sends each image once, 12 at most with the default settings, so about 4 cents at most. That cost is on the Google Cloud project. `INVESTIGATE_MONTHLY_CAP_USD` does not count it.

How the report ranks Google's matches is a design choice you may want to change. Google names no artist, and a picture that is all over the web brings a page for every copy. So Google's first four matches for an image are ranked with the archives' matches and later ones go behind everything else, an archive's entry wins when both find the same page, and Google's matches are left out of the note that says a set of images names several different artists.

## The move to Node 24

Decision 5 was to move the whole host through apt, together with this deploy. The host now runs Node 24.22.3 from the NodeSource apt package, with npm 11.19.1.

What was checked first, in a temporary directory on the host and without touching a running app:

- A Node 24.22.3 unpacked into that directory installed both lockfiles: the bot in 10 seconds, the dashboard in 18.
- Every package the bot and the dashboard import loaded under it, the compiled ones included (better-sqlite3, sharp, canvas, the Sentry profiler).
- The other Node apps on the host: their compiled modules were rebuilt in a copy and loaded, and their other dependencies loaded from where they are.
- PM2 ran a full cycle (start, restart, save, kill, resurrect) as a second daemon with its own home directory.
- apt, in a simulation with the Node 24 source: one package upgraded, nothing removed, nothing new.

Two things on the host shaped the procedure:

- **`needrestart`.** Ubuntu's `needrestart` restarts services by itself after an apt install when a binary or library they run was replaced. It did that on 2026-11-13 after an unattended libc upgrade: the PM2 daemon and every app under it went down and came back twelve seconds later. A plain `apt install nodejs` would have restarted every app at once on Node 24, with compiled modules that were still built for Node 20. So the install ran with `NEEDRESTART_SUSPEND=1`, and the apps were restarted one at a time, each with a check.
- **The deploy skipped the install after a Node change.** `./deploy.sh` decided by the lockfile's hash alone whether `node_modules` was current. The key now also holds the module ABI number of the host's Node, so the deploy after the switch reinstalled in both directories, and a deploy after a way back would do the same.

The release went out on Node 20 first and the host moved second. That way each of the two changes was checked by itself, and each has its own way back.

From here on:

- A newer Node 24 does not install itself. Unattended upgrades take packages from Ubuntu's own archives only, and Node comes from NodeSource, so a patch release arrives with a manual `sudo apt upgrade`.
- That upgrade lets `needrestart` restart the PM2 unit and the other Node service by itself. Inside Node 24 that costs a few seconds and nothing else: compiled modules stay valid for the whole major version. Put `NEEDRESTART_SUSPEND=1` in front if you want to pick the moment yourself.
- The next major version is this procedure again.

## Rolling back

**The bot and the dashboard.** Check out `46097bbe`, the commit 26.0.0 was built from, and run `./deploy-no-tests.sh`. Then run `npm run deploy:cmds` on the host, which takes `/service-keys` out of Discord again. The database needs nothing: 26.0.0 runs without the two dropped indexes, because nothing read them. The keys that `/service-keys` wrote stay in `.env` and 26.0.0 reads them at start.

**The two indexes.** If you want them back, the statements are in the header of `migrations/085_drop_unused_msgarc_indexes.ts`. Creating both took six seconds on the rebuilt copy.

**Node.** The set is in `/home/ubuntu/node20-rollback/`, with these steps in its `README.txt`. Put the saved source file back and install the saved package, again with needrestart suspended:

```bash
sudo cp /home/ubuntu/node20-rollback/nodesource.sources /etc/apt/sources.list.d/nodesource.sources
sudo apt-get update
sudo env NEEDRESTART_SUSPEND=1 apt-get install -y --allow-downgrades nodejs=20.20.2-1nodesource1
```

The package file itself is in the same directory, for the day NodeSource no longer offers it: `sudo env NEEDRESTART_SUSPEND=1 dpkg -i` on it does the same. Then the other apps, one at a time: put the compiled module from before the switch back (the `*.abi115` files in that directory) or rebuild it, and restart the app. For the bot and the dashboard run `./deploy.sh`, which reinstalls because the Node changed. Last, restart the PM2 unit and the other Node service.

## What was not verified

- `/service-keys` and the new report as real Discord interactions. There is no test server. They are tested with mocks; their first real run is yours.

- A Google web detection answer with matches. Google refuses the stored key, so the reading of an answer follows Google's published format and has only run against stubbed answers. Against the live service the adapter ran once, with a key that cannot exist, and Google refused it as expected.
- The index numbers on the host's own hardware. The write test ran on the dev machine, on a table rebuilt from the production table's keys. The planner check and the sizes are from the host.
- A level-up line in production. The fix is tested, but no member leveled up between the deploy and the last check, so the host's log does not hold such a line yet.
- A reboot of the host on Node 24. The PM2 unit was restarted and brought every app back, and the units are enabled at boot. The machine itself was not rebooted.
- That a manual `apt upgrade` restarts the Node services by itself. It follows from how `needrestart` is set up on the host and from what it did on 2026-11-13 after an unattended upgrade. It was not tried.
