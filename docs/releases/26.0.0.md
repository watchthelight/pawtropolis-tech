# Pawtropolis Tech 26.0.0

Released on 2026-11-14 (US Eastern). Production has run 26.0.0 since 2026-11-15 03:15 UTC, built from commit `46097bbe` of `release/v26`. `main` was fast-forwarded to the branch after the deploy.

This is the end-of-2026 release. It adds one command and cleans up a lot underneath. The full list is in [`CHANGELOG.md`](../../CHANGELOG.md), and the audit behind it, with everything that was deferred, is in [`MODERNIZATION_PLAN.md`](../../MODERNIZATION_PLAN.md).

## What you will notice

**`/investigate-artist`.** Run it inside a 2D artist verification ticket. It reads the whole ticket, fetches every image the applicant posted, runs reverse image lookups, looks at the applicant's history in the server, and asks Claude to rate the application against the handbook's own criteria. You get a private reply: an advisory score, a breakdown per criterion with the evidence, every lookup match with its link, flags, follow-up questions to ask, and what it could not determine.

- Only user IDs in `OWNER_IDS` can run it. Everyone else gets a one-line refusal.
- The reply is ephemeral and nothing is posted in the ticket.
- It never approves, denies, changes roles or messages the applicant. Stolen, traced and AI-made art cannot be detected reliably, so it gives indicators with reasoning, not a verdict.
- It cannot open videos or source files such as `.psd` and `.clip`. It lists them by name. Those are the proofs the workflow leans on most, so open them yourself.
- Three test runs on a real four-image ticket took 64 to 78 seconds and cost 0.17 to 0.18 USD each. The footer of every report shows that run's cost and the month's total, and the command refuses to run once the month would pass `INVESTIGATE_MONTHLY_CAP_USD` (200 by default).

**Three security holes are closed.** Dashboard sessions could be forged with a hand-written cookie. A failed `/update banner` or `/update avatar` could print the GitHub bot token in a public channel. The bot's internal dashboard API listened on every network interface.

**Eleven reliability bugs are fixed.** The ones staff could have met: panic mode switching itself off after a restart, an applicant whose modmail could never be opened again, `/redeemreward` taking a ticket and then finding no artist, queued welcome messages lost on restart, and slash commands logged as timeouts while they were still working.

**Two numbers change.** Weekly active users in the Stats Observatory and the daily chart on Pulse were wrong, and now they are right. Expect weekly active users to go up and the daily chart to show real message counts instead of 1.

**Some things are faster.** The activity check in `/audit members` takes 0.3 seconds per 100 members instead of 13.7. The `/activity` heatmap query is two to three times faster. Encoding leaderboard and heatmap images no longer stalls the bot.

## What is left for you

1. **Run the command once.** In Discord, type `/investigate-artist` in a 2D artist ticket you already know well, and compare the report with your own read. This is its first run as a real Discord command. Discord shows it to members with Administrator. The one ID in `OWNER_IDS` belongs to a member with Administrator, and the server has no permission overrides on the bot's commands, so it shows up for you.
2. **Do one dashboard action that calls the bot**, such as a config change. You will be asked to sign in first: cookies from before the encryption change are no longer accepted. The path from the dashboard to the bot was checked on the host, not from a signed-in browser.
3. **Run `/sync-tasks`.** The todos of this release are not on GitHub Issues yet. A dry run would create 15 issues, update 1 and close 1. Six of the 15 and the one it closes are older than this release, so the run was left to you.
4. **Delete two directories on the host** once 26.0.0 has run for a few days. They are listed under "Left on the host".
5. **Close `todo/00285.md`** when you are happy with the release in production.

The decisions that wait for you are in `MODERNIZATION_PLAN.md`, section 7, and in `todo/00287.md`. The ones closest to this release: rotating `GITHUB_BOT_TOKEN`, the two held branches (`hold/v26-one-open-ticket-per-type` and `hold/v26-untrack-playwright-mcp`, each one commit on top of the release and neither pushed), free SauceNAO and e621 accounts for the lookups, the seven dead cron jobs, and moving the host from Node 20 to Node 24.

## Environment keys

| Key                           | On the host                   | What it is                                                                                                                                    |
| ----------------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `OWNER_IDS`                   | Was already set               | Your Discord user ID. Comma-separated if there are several. Empty means the command refuses everyone.                                         |

## How it went out

The deploy ran before anything was pushed. The branch describes the session forgery hole in the dashboard, and production was open to it until 26.0.0 was running. So the fix went live first and the code became public second.

Before the deploy, on the host:

- Node is 20.20.2 with npm 10.8.2, which meets the 20.9.0 floor.
- Both lockfiles were installed in a directory of their own, away from the app. Every package the bot and the dashboard import loaded there, the native ones included (better-sqlite3, sharp, canvas), and the bot bundle linked. A dry run of the migration runner against the production database listed one pending migration, 084.
- That trial install took 204 seconds for the dashboard, 174 of them compiling better-sqlite3 12.11.1, which has no prebuilt binary for Node 20. The dashboard went back to 12.6.2 (`46097bbe`) and the same install took 15 seconds.
- Everything the deploy replaces was copied to a rollback directory: the deployed files, both `node_modules` directories and the `.env`.
- The two keys were added to `.env`. A models request from the host, with the key and workspace read from that file, was accepted and listed `claude-opus-5-5`.

That `npm ci` was the first one the deploy script ever ran on this host. Its lockfile check had been comparing the uploaded lockfile with itself since March 2026, so it always skipped the install, and the host's packages dated from May (`MODERNIZATION_PLAN.md`, TCD-23). What went was development tooling such as eslint and babel, and dependencies that had left `package.json` since the last install, `@google-cloud/vision` among them. The dashboard went from 356 to 336. Every package the bot and the dashboard load had been loaded from a clean install in the trial directory first.

Pushing `main` starts the dashboard deploy workflow, because the release changes `web/` and `docs/`. It builds the dashboard from `main` on GitHub, uploads it and restarts `pawtropolis-web`. This file is part of the push that starts it, so the result of that run is in `todo/00285.md`.

Checked after the restart:

- PM2 shows both apps online at version 26.0.0 with one restart each, the one from the deploy. The other apps on the host were not restarted.
- The bot log has no warning and no error in its first 14 minutes, and nothing on stderr.
- `artist_investigation_run` and `artist_provenance_cache` exist, and `PRAGMA quick_check` on the database says ok.
- Both `node_modules/.lock-sha256` markers match their lockfiles, so the next deploy skips the install unless a lockfile changes.
- The internal dashboard API listens on `127.0.0.1:3003` only. From the host, the dashboard's configured URL reaches it: the health route answers 200 with the shared secret and 401 without.
- The dashboard answers on the host and through Cloudflare, and `/dashboard` redirects to the sign-in page.
- Discord lists `/investigate-artist` for the guild, with Administrator as its default permission. The bot has the permissions it needs to read a ticket.
- `scripts/cleanup-backups.sh` on the host is still the working version, and still executable.

## Rolling back

The rollback set is in `/home/ubuntu/pawtropolis-rollback-7.0.0`, with these steps in its `README.txt`:

```bash
cd /home/ubuntu/pawtropolis-tech
pm2 stop pawtropolis pawtropolis-web
mv node_modules ../pawtropolis-rollback-7.0.0/node_modules.v26
mv web/node_modules ../pawtropolis-rollback-7.0.0/web-node_modules.v26
mv ../pawtropolis-rollback-7.0.0/node_modules node_modules
mv ../pawtropolis-rollback-7.0.0/web-node_modules web/node_modules
tar -xf ../pawtropolis-rollback-7.0.0/app-files.tar
npm run deploy:cmds
pm2 startOrRestart ecosystem.config.cjs
```

The database needs nothing. Migration 084 only added two tables, and 7.0.0 does not read them. The two new keys in `.env` are ignored by 7.0.0. `npm run deploy:cmds` puts the 7.0.0 command list back, which removes `/investigate-artist` from Discord. The old `node_modules` directories are kept because they cannot be rebuilt from the 7.0.0 lockfile.

If only a dashboard action fails, there is a smaller fix: set `DASHBOARD_API_HOST=0.0.0.0` in the host `.env`, then `pm2 restart pawtropolis`.

## Left on the host

- `/home/ubuntu/pawtropolis-rollback-7.0.0`, about 1.0 GB: the rollback set, readable by the deploy user only. It holds a copy of the `.env` from before the two keys were added.
- `/home/ubuntu/pawtropolis-v26-preflight`, about 0.7 GB: the trial install and the small scripts that ran the checks above.
- Two database copies of 1.29 GB each, named in the table above. The daily cleanup job prunes them by its usual rule, the three newest plus seven days.

Remove the two directories when you no longer want the way back:

```bash
ssh bash-ec2 "rm -r /home/ubuntu/pawtropolis-rollback-7.0.0 /home/ubuntu/pawtropolis-v26-preflight"
```

Nothing else on the host was changed: not the crontab, not nginx, not the other PM2 apps.

## What was not verified

- `/investigate-artist` has never run as a real Discord command. There is no test server, so it was tested with mocks and with three local runs that read a real ticket and printed the report to a file. Its first run in production is its first run in Discord.
- SauceNAO and e621 have never returned a real match, because no keys exist yet.
- A dashboard action from a signed-in browser. The route it uses was called from the host instead.
- A real `git push` through the new token handling in `/update banner` and `/update avatar`. It is covered by unit tests only.
- The reliability fixes under real traffic. Each has tests, and the bot had run for a quarter of an hour when this was written.
