# #00239 -- Wide-event Response State is inaccurate for handlers that defer/reply directly instead of via cmdWrap helpers

**Type:** bug | **Priority:** Low

markDeferred() is only emitted inside ensureDeferred() and markReplied() only inside replyOrEdit(). The large majority of component/modal handlers call interaction.deferUpdate()/deferReply()/update()/reply()/editReply() DIRECTLY (e.g. byteTokenHandler, artistRotation/handlers, modmail/handlers, qotd/handlers, tickets/handlers, dmVerification). For those flows the wide event's responseState.deferredAt/repliedAt stay null, so the error card's 'Response State' section (errorCardV2.ts:288-325) reports 'Deferred: No (direct reply or error before defer)' and 'Replied: No' even though the user definitely received a response. This degrades the exact debugging signal the wide-event system was built to provide ('did the user see anything?').

**Location:** `src/lib/cmdWrap.ts:456-457,515-516`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Either funnel direct defer/reply calls through the cmdWrap helpers, or add lightweight enrichEvent(e=>e.markDeferred()/markReplied()) calls in the shared handler entry points, so response-state telemetry reflects reality.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0272. See audit/2026-05-31/full-codebase-audit.md.
