# #00247 -- Modmail context-menu defers and replies PUBLICLY, unlike the button path which keeps failures ephemeral

**Type:** bug | **Priority:** Low

handleModmailContextMenu calls interaction.deferReply() with no MessageFlags.Ephemeral (line 190) and then interaction.editReply({content: result.message}) (line 239), so both the 'Bot is thinking...' state and the final outcome message (including failure strings like 'Failed to create modmail thread. Check bot permissions.') are PUBLIC in whatever channel the staffer right-clicked a message in. The sibling button handler handleModmailOpenButton deliberately keeps the failure path ephemeral (followUp with flags:Ephemeral, lines 125-131) and only posts success publicly. The inline comment at line 188 ('Context menus don't support deferUpdate, so we use deferReply') justifies the deferReply but not the missing Ephemeral flag. Impact: a permission/setup failure when opening modmail from a context menu is broadcast to the channel rather than shown privately to the acting moderator, and the public 'thinking' bubble appears in a potentially user-visible channel.

**Location:** `src/features/modmail/handlers.ts:185-240`
**Category:** ephemeral-flags | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Pass flags: MessageFlags.Ephemeral to deferReply() in handleModmailContextMenu so the staffer's interaction matches the ephemeral semantics of the button path; post the public 'thread created' confirmation via interaction.channel.send (as the button path does) instead of via the public editReply.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0325. See audit/2026-05-31/full-codebase-audit.md.
