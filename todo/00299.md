# #00299 -- A new database cannot be built from the repo

**Type:** bug | **Priority:** Low

Found on 2026-11-15, after the cutover of #00295, while the leftovers of the first research pipeline were looked at. Production is not affected: its database has every table and every migration. This is about a database that starts empty, such as a development copy in a fresh clone, a second server, or a rebuild without the old file.

- **The migrations do not start from nothing.** `tsx scripts/migrate.ts --init` on a new file applies 001 to 003 and stops at 004 with `no such table: main.action_log`. Tried on a scratch file. Some base tables are made by the bot and not by a migration: `src/db/db.ts` creates twelve when it is imported, and the steps in `src/startup/schema.ts` can create more when the bot is ready, `action_log` and `guild_config` among them. So the bot would have to start once before the first migration. No document says so.
- **The `application` table is created nowhere.** No file in `src/`, `migrations/` or `scripts/` holds its `CREATE TABLE`. It exists in the production database and in `tests/fixtures/schema.sql`, which is a dump of a migrated database with 101 tables. The fixture is the only complete schema in the repo.
- **Migration 070 cannot pass on a new database.** It creates indexes on `general_messages_effort`, `general_messages_resonance`, `general_messages_score` and `general_messages_raw`. Migration 069 made those tables, and it left the repo with the first pipeline on 2026-05-15 (`62283076`). Run against a database without them, 070 stops at its first statement with `no such table: main.general_messages_effort`. The runner ends at the first failed migration, so 071 to 086 would never be reached.
- **Three rows of `schema_migrations` on the host are doubles.** The table has 83 rows: the 79 migrations of the repo, `069`, and `58.0`, `62.0` and `63.0`, which carry the names of 058, 062 and 063. The runner compares the three-digit versions, so the doubles do nothing. They are left from an earlier way of writing the version.

**What would fix it.** One way to make a new database that is written down and tested. The shortest would be a `--init` that loads `tests/fixtures/schema.sql` and marks every migration as applied, because the fixture is the schema after all of them. Migration 070 then still needs its four index statements on the study's tables taken out, or made to depend on the table being there. A test that builds a database from nothing and compares it with the fixture would keep it that way.

**Not checked.** Whether migrations 004 to 068 pass on a database that the bot's start code has prepared. Whether the bot starts at all on an empty file, where `application` is missing.

**Why it has not hurt.** The tests build their database from the fixture, and `npm run gen:test-schema` makes the fixture from a migrated database. Production and the development copy both hold a database that is older than these gaps.
