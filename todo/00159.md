# #00159 -- Transient member-fetch failure poisons the permission cache with a public-only list

**Type:** bug | **Priority:** Low

All help entry points fetch the member with `members.fetch(userId).catch(() => null)` and tolerate null (autocomplete.ts:53, index.ts:90/319/397/461). When the fetch rejects (Discord API hiccup/rate limit - explicitly anticipated by the code comments), member is null and filterCommandsByPermission is called with member=null. hasPermissionLevel(line 213) then returns true only for `public` (and bot owner), so the result is the public-only command list - and that list is cached under `${guildId}:${userId}` for 5 minutes (line 283). Because autocomplete fires on every keystroke and is usually the first help interaction, a single failed fetch there poisons the shared module-level PERMISSION_CACHE, so the subsequent `/help` execute and the showCommandDetail permission gate (index.ts:220) both serve the stale public-only list, falsely hiding staff/reviewer/admin commands and denying their detail view for the whole TTL. Combined with the fact that invalidatePermissionCache is never wired up, nothing clears it early.

**Location:** `src/commands/help/cache.ts:260-289`
**Category:** correctness | **Confidence:** medium | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Do not cache results computed from a null member (skip PERMISSION_CACHE.set when member is null), or treat a fetch failure as 'unknown' rather than 'public-only' and bypass the cache. Alternatively key the cache on resolved role IDs so a null-member computation can't masquerade as a real permission set.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0045. See audit/2026-05-31/full-codebase-audit.md.
