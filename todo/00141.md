# #00141 -- Per-migration transaction does not roll back side effects that do not throw, and version is stamped even for n

**Type:** bug | **Priority:** Medium

applyMigration wraps migrateFn in db.transaction (lines 209-213), but as the in-file GOTCHA at 206-208 notes, the transaction only rolls back on a thrown exception. A migration that performs a partial/incorrect change without throwing still commits, and because each migration calls recordMigration itself (inside the same transaction), the version is permanently marked applied. Since the deploy harness above (deploy.sh:435) also swallows failures, a migration that logs an error but exits the function normally will be recorded as applied and never retried. Combined, there is no end-to-end guarantee that 'recorded as applied' means 'schema is correct'.

**Location:** `scripts/migrate.ts:205-213`
**Category:** deploy-safety | **Confidence:** medium | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Have the runner (not each migration) own the stamping: only call recordMigration after migrateFn returns AND after a post-condition check where feasible. Surface any migration-internal error by throwing rather than logging-and-returning. Pair with fixing the deploy.sh swallow so a throw actually aborts.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0295. See audit/2026-05-31/full-codebase-audit.md.
