# #00221 -- closed_at parsed as local time instead of UTC, skewing the 7-day reopen window

**Type:** bug | **Priority:** Low

closeTicket() (tickets.ts:165) writes closed_at via SQLite datetime('now'), which yields a UTC string of the form 'YYYY-MM-DD HH:MM:SS' with NO timezone designator (the schema column is closed_at TEXT, db.ts:187). Line 73 does `new Date(ticket.closed_at).getTime()`. V8/Node parses a space-separated, zone-less datetime string as LOCAL time, not UTC. So `closedAt` is offset from the true close instant by the server's UTC offset. The 7-day boundary test on line 77 (`now - closedAt > sevenDays`) is therefore wrong by up to the host UTC offset (~14h max). On a server with a positive UTC offset this makes `now - closedAt` larger than reality, so a ticket closed at ~6.8 days can be mis-classified as >7 days and a brand-new thread is created (via openPublicModmailThreadFor) instead of reopening the existing one; on a negative-offset server the window stays open too long. This is confirmed to be an inconsistency in THIS codebase: the correct normalization pattern is used elsewhere for the same kind of SQLite timestamp (src/ui/reviewCard.ts:110 and src/features/review/card.ts:129 both do `trimmed.replace(' ', 'T') + 'Z'` before new Date()). The identical raw-parse bug also exists in src/features/modmail/dashboardBridge.ts:304 (out of bucket) for the same field.

**Location:** `src/features/modmail/threadReopen.ts:73,77`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Normalize the SQLite UTC string before parsing, e.g. `const iso = ticket.closed_at.includes('T') ? ticket.closed_at : ticket.closed_at.replace(' ', 'T') + 'Z'; const closedAt = ticket.closed_at ? new Date(iso).getTime() : 0;` (reuse the existing helper used by reviewCard.ts / review/card.ts). Apply the same fix at dashboardBridge.ts:304.
