# #00136 -- Stale push subscriptions keep receiving tier-gated PII after a user is demoted or removed

**Type:** security | **Priority:** Medium

Tier on a push subscription is only refreshed reactively when a 'role:changed' SSE event arrives (updateTier on lines 87-96). If a moderator is demoted or leaves the guild while the bot/web is down, or if the role:changed event is never emitted for that user, their stored `tier` stays at the old (higher) value. pushBroadcast then still passes the hasMinTier check (line 122) and sends notifications whose body/data include sensitive content - applicant display names (review:submitted body, line 63) and appId, and modmail/audit context - to a device that should no longer have access. There is no authoritative re-check of the subscriber's current roles at send time; tier is trusted from the local push.db row.

**Location:** `web/src/lib/server/push/push-sender.ts:86-152`
**Category:** security | **Confidence:** medium | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Treat the stored tier as a cache only: re-resolve the user's current tier at send time (or on a short TTL) via the Discord role source / session, and/or proactively delete subscriptions on demotion and guild-leave events. At minimum, run deleteStaleSubscriptions on role loss and verify tier against a fresh roles lookup before sending tier-restricted payloads.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0247. See audit/2026-05-31/full-codebase-audit.md.
