# #00118 -- Garbled claim error during panic mode (fragile message string parsing)

**Type:** bug | **Priority:** Medium

On a failed claim, INVALID_STATUS is rendered as `Cannot claim: application is already **${err.message.split(" ")[2]}**.` This assumes the ClaimError message is always the terminal-state form "Application already <status>" (split()[2] == status). But claimTx() throws the SAME INVALID_STATUS code for panic mode with message "Panic mode is active. All review operations are suspended." (reviewActions.ts:62). split(" ")[2] of that string is "is", so during panic mode a moderator clicking Claim sees the nonsensical message "Cannot claim: application is already **is**." It also needlessly calls ensureReviewMessage() to "refresh card after blocked claim" even though nothing changed. The claim is still correctly blocked, so this is cosmetic/diagnostic, but it actively misleads the operator during an emergency (panic) when clear messaging matters most.

**Location:** `src/features/review/handlers/claimHandlers.ts:49-60`
**Category:** correctness | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Do not parse the human message. Either (a) carry the status as a structured field on ClaimError (e.g. add a `status?` property set when throwing terminal-state errors) and render that, or (b) add a distinct error code for panic (e.g. "PANIC_MODE") and branch on it explicitly so panic shows "Review operations are suspended (panic mode)."

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0124. See audit/2026-05-31/full-codebase-audit.md.
