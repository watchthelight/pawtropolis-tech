# #00265 -- Perf pass T3: DB layer, pragmas, indexes, retention

**Type:** refactor | **Priority:** Medium | **Status:** `WIP`

Fourth tier of the performance plan. Retention deletes ship behind `RETENTION_ENABLED` with a dry-run count first.

**Items**

1. Pragmas: web `cache_size` 256 MB -> 64 MB and `mmap_size` 1 GB -> 256 MB; bot adds `mmap_size` 256 MB and `journal_size_limit` 64 MB; `PRAGMA optimize` on shutdown and daily; one-off `ANALYZE` migration.
2. Indexes (add only where `EXPLAIN QUERY PLAN` shows a scan): `modmail_message(ticket_id, created_at)`, `modmail_message(direction, created_at)`, `review_action(moderator_id, created_at)`, `review_claim(reviewer_id)`, `user_activity(guild_id, first_message_at)`, `security_issue_history(guild_id, recorded_at)`.
3. `messages_archive` retention (owner decision: 365 days live, monthly cold archive to R2).
4. Retention for `security_issue_history`, `consumed_confirmations`, `member_role_snapshots`, `config_audit_log`, `guild_snapshot_log`; all in one retention scheduler with chunked deletes.
5. `action_log_fts` catch-up in batches (index is stale since migration 073).
6. `scripts/migrate.ts`: skip the pre-migration copy when no migration is pending, use the online backup API, retention 5 -> 2.

**Update 2026-09-01:** items 1, 5 and 6 landed (1a6b9767, 5d45db90, 6498b42a); the migrate script already skipped the copy when nothing was pending, so only the backup API and retention changed. The retention scheduler ships in dry-run mode: it logs candidate counts daily and deletes only with `RETENTION_ENABLED=true`.

Item 2: `EXPLAIN QUERY PLAN` against the local copy showed every candidate already served by an existing index (`idx_modmail_message_ticket_time`, `idx_review_action_actor_time`, `idx_application_guild_status_created`); no index was added. The one-off ANALYZE migration was replaced by a bounded `PRAGMA optimize` (daily and at shutdown), which analyses only tables whose shape changed.

Items 3 and 4, and the real storage finding: `dbstat` on the local copy (5.1 GB) puts 4.5 GB in the `general_messages_*` tables (`general_messages_embed` alone is 3.7 GB of vector BLOBs, plus ctx, score, raw, effort, resonance and their indexes). Nothing under `src/` or `web/src` reads them; they are written only by `scripts/local-pipeline.mjs`, `scripts/export-embed.mjs` and the `quality-*` scripts. `messages_archive` is not in the top 18 tables locally. If the production file carries the same tables, moving that pipeline to its own database file is the storage fix, and quick_check, backups and Litestream all get cheaper with it. Archive retention is therefore still an owner decision and was not implemented.
