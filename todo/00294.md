# #00294 -- Drop the two unused indexes on messages_archive

**Type:** chore | **Priority:** Medium

Owner decision 11 (#00287), from PERF-7 and PERF-8 of the v26 audit. Done in 26.1.0 by migration 085.

Measured on the host on 2026-11-15, read-only: the database is 1,227 MB, 673 MB of tables and 555 MB of indexes. 22 indexes repeat the leading columns of another index on the same table, but together they take 7.8 MB, so they stay.

The weight is on `messages_archive` (3.29 million rows): `idx_msgarc_author_time` (105 MB) and `idx_msgarc_channel_time` (103 MB). `idx_msgarc_guild_time` (102 MB) stays.

The drop had two conditions. Both hold.

**Nothing uses them.** Every statement in the bot, the dashboard and the scripts that touches the table went through `EXPLAIN QUERY PLAN` on the production database, with its own statistics:

- The update that marks a message as deleted goes through the primary key.
- Everything else filters by guild and goes through `idx_msgarc_guild_time`: the reaction list of the stats refresh and the queries of `scripts/report/` (totals, first and last message, per year, month, day, hour, channel and author).
- No statement picks either of the two. No code names an index with `INDEXED BY`, and nothing else on the host reads the table.

**They cost something.** The local copy of the database has no archive rows, so the table was rebuilt: the key columns and the byte length of every text field were exported from the host (no message text, no names), inserted locally in the same order with filler of the same length, and packed with `VACUUM`. The three indexes of the rebuilt table are within 2% of their size on the host.

The workload is the last 45,000 rows of the real table (2026-10-24 to 2026-11-15, about 2,100 rows a day): 5,000 to warm up and 40,000 measured, with the bot's own insert statement and connection settings, rows of the same second in one transaction like the bot's one-second flush. Five rounds in alternating order on the dev machine, a fresh copy for every run.

- Time for the 40,000 rows, median of five: 6,846 ms with the three indexes (5,655 to 8,647), 3,181 ms with the guild index alone (2,942 to 4,768).
- Written to the WAL: 908 MB against 486 MB, which is 5.78 against 3.09 pages a row.
- File size: grew from 942 to 957 MB with the three indexes, stayed at 942 MB without the two.

So an archived message takes a little under half the time and a little over half the page writes. In absolute terms the time is small, about 0.36 against 0.17 seconds of database time a day at the present rate. The volume written and the space are what change.

The drop puts 51,822 pages (202 MB) on the free list of the rebuilt table; on the host it is the 208 MB of the two indexes. The workload took 2,757 of those pages, so the freed space holds about 750,000 messages, roughly a year at the present rate, before the file grows again. The file itself does not shrink: `auto_vacuum` is off on the host, and a `VACUUM` is not part of this change.

The reports do not change. The two heaviest report queries group the whole archive by channel and by author. Median of three runs: 3,330 ms before and 3,479 ms after for the first, 3,805 and 3,816 ms for the second, with the same plan before and after. Forced onto the dropped indexes with `INDEXED BY` they take 2,079 and 3,136 ms, so the two indexes could have helped these two queries, but only if the queries had named them.

Migration 085 drops the two indexes and then checks that they are gone and that `idx_msgarc_guild_time` is still there. On the rebuilt table the two drops took 135 and 116 ms and wrote 0.2 MB. To get the indexes back:

```sql
CREATE INDEX idx_msgarc_author_time ON messages_archive(author_id, created_at_s);
CREATE INDEX idx_msgarc_channel_time ON messages_archive(channel_id, created_at_s);
```

That took 3.4 and 2.7 seconds. Each index goes through the WAL in one piece of about 100 MB, and writes to the database wait while it is built.

Not measured: the host's own hardware. Every time above is from the dev machine, so the ratios carry over and the absolute times do not. The planner check and the sizes are from the host.

The research pipeline (#00295) does not read this table: it fills its own from Discord. Should it come to read one channel out of the archive, a read by guild and time window still goes through the kept index. Reading one channel's whole history often would be the reason to create `idx_msgarc_channel_time` again.
