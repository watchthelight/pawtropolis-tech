# #00072 -- `modmail_delete_on_close` opt-out is silently ignored - threads always deleted on close

**Type:** bug | **Priority:** High

Both close paths compute the delete decision as `cfg?.modmail_delete_on_close !== false` (line 365 in `closeModmailThread`, line 546 in `closeModmailForApplication` feeding `archiveOrDeleteThread`). The `GuildConfig` type declares `modmail_delete_on_close?: boolean | null`, but that is a type-level lie. The column is created as `INTEGER DEFAULT 1` (src/lib/config.ts:375, ensureModRolesColumns), the config command stores the boolean via upsert which converts `false`->integer `0` / `true`->`1` (src/lib/config.ts:687; src/commands/config/setFeatures.ts:300-304), and `getConfig` does `SELECT *` and returns the raw row with no boolean coercion (src/lib/config.ts:707-724). So at runtime `cfg.modmail_delete_on_close` is the NUMBER `0` or `1`, never a boolean. `0 !== false` evaluates to `true` (strict inequality: number 0 is not boolean false), so `preferDelete`/`deleteOnClose` is `true` even when an admin explicitly set 'Delete on Close = off' (stored as 0). Impact: every modmail close DELETES the Discord thread regardless of the setting, irreversibly destroying the in-channel thread/history against explicit admin opt-out. The opt-out path (archive+lock, keep thread) is unreachable.

**Location:** `src/features/modmail/threadClose.ts:365, 546`
**Category:** correctness | **Confidence:** high | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** Compare the integer truthiness instead of strict boolean inequality. Either coerce in getConfig (e.g. `modmail_delete_on_close: config.modmail_delete_on_close == null ? null : !!config.modmail_delete_on_close`) or change the consumers to `const preferDelete = cfg?.modmail_delete_on_close !== 0 && cfg?.modmail_delete_on_close !== false;` (default true only when null/undefined). Cleanest: normalize all INTEGER-boolean config columns to real booleans on read in getConfig.
