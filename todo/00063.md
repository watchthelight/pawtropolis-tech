# #00063 -- Failed remote DB migration is swallowed, then PM2 restarts new code against an un-migrated database

**Type:** bug | **Priority:** Critical

Step 6.5 runs the migration as: ssh_remote "cd ${REMOTE_PATH} && node scripts/migrate-remote.js" || echo "Migration step completed (may have warnings)". Because the failure branch is `echo` (which always exits 0), a non-zero exit from the migration is discarded even under `set -euo pipefail`. Control then proceeds to Step 7 (lines 449-455) which unconditionally runs `pm2 startOrRestart ecosystem.config.cjs`, bringing up the new bot + web code against a database whose schema was NOT migrated (or was left half-migrated). docs/reference/database-schema-safety.md:13 explicitly promises the opposite: 'If a migration fails, the rest of the deploy bails.' This is the single highest-impact ops defect: a migration error produces a green-looking deploy and a running bot that will throw at runtime on missing columns/tables (see src/config/flaggerStore.ts:211 which already handles 'column missing - migration may not have run'). The pre-deploy backup (maybe_backup_remote_db) does not help because the code is still rolled forward on top of the old schema.

**Location:** `deploy.sh:435,449-455`
**Category:** deploy-safety | **Confidence:** high | **Audit severity:** critical (adversarially confirmed)

**Suggested fix:** Do not swallow the migration exit code. Either remove the `|| echo ...` so `set -e` aborts, or capture status explicitly and abort before the PM2 restart, e.g.: `if ! ssh_remote "cd ${REMOTE_PATH} && node scripts/migrate-remote.js"; then echo 'ERROR: migration failed, aborting deploy (code NOT restarted)'; exit 1; fi`. Keep the lock trap so the lock is released on abort.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0289. See audit/2026-05-31/full-codebase-audit.md.
