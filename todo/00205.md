# #00205 -- Garbled user-facing message for INVALID_STATUS claim errors (esp. panic mode)

**Type:** bug | **Priority:** Low

For err.code === 'INVALID_STATUS' the handler builds the message via err.message.split(' ')[2] to extract the status word. claimTx throws INVALID_STATUS in two cases: (1) terminal status, message 'Application already <status>' -> split[2] = '<status>' (works); (2) panic mode (src/features/reviewActions.ts:60-62), message 'Panic mode is active. All review operations are suspended.' -> split(' ')[2] = 'is'. So when a guild is in panic mode and a moderator clicks Claim, they see 'Cannot claim: application is already **is**.' instead of the panic-mode notice. This is misleading exactly during an emergency lockdown. The technique (parsing a human-readable Error.message by word index) is also brittle to any future wording change.

**Location:** `src/features/review/handlers/claimHandlers.ts:49-51`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Carry structured data on ClaimError (e.g., a `status` field or a distinct PANIC code) and branch on that instead of string-splitting the message. At minimum, special-case the panic-mode message (or add a PANIC ClaimError code) so the reply reads 'Panic mode is active; review operations are suspended.'

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0106. See audit/2026-05-31/full-codebase-audit.md.
