# #00177 -- Heatmap builder issues one query per week (up to 26) and pulls every raw message row into JS instead of aggreg

**Type:** bug | **Priority:** Low

getHeatmapDataForRange() loops weeksCount (capped MAX_WEEKS=26) and calls buildWeek() each iteration (lines 180-183). buildWeek() runs 'SELECT created_at_s FROM message_activity WHERE guild_id=? AND created_at_s>=? AND created_at_s<?' (122-127) returning EVERY raw message row for that week, then buckets them in a JS loop (144-150). So a 26-week window = 26 separate queries, each potentially returning tens of thousands of rows, all materialized and iterated in Node on the SSR path. message_activity already has hour_bucket plus idx_message_activity_guild_hour, so the entire grid could be one GROUP BY. Mitigated by the 60s page cache (heatmap/+page.server.ts:20) but every cold load / new window pays it.

**Location:** `web/src/lib/server/queries/heatmap.ts:121-190`
**Category:** perf | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Replace the per-week raw-row fetch with a single query over the whole range that GROUPs BY hour_bucket (or by day-of-week/hour), e.g. SELECT (created_at_s/3600)%24 ... COUNT(*) GROUP BY ..., then distribute counts into the week grids in JS. This turns 26 row-streaming queries into one aggregate query and removes the per-row JS bucketing.
