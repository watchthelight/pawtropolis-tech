# #00126 -- Monthly leaderboard/stats compare ISO-8601 string against SQLite datetime('now') format, undercounting month-b

**Type:** bug | **Priority:** Medium

getMonthlyLeaderboard and getArtistStats compute the month start with `new Date(); setDate(1); setHours(0,0,0,0); .toISOString()`, producing a string like '2026-05-01T00:00:00.000Z' (with 'T' separator, milliseconds, and 'Z'). They then compare `completed_at >= startIso`. But completed_at is written by `datetime('now')` (store.ts:297) which produces SQLite's canonical format '2026-05-01 00:00:00' (SPACE separator, no ms, no 'Z'). The two formats are compared lexically. At character index 10 the stored value has ' ' (0x20) while the bound has 'T' (0x54); since ' ' < 'T', any job whose completed_at date-part equals the boundary day (the 1st of the month at/after midnight) compares as LESS THAN startIso and is wrongly excluded from the monthly count. Additionally, toISOString() converts LOCAL midnight to a UTC instant while completed_at is stored in UTC, so the boundary is further skewed by the server's UTC offset. Net effect: a recurring, silent undercount of jobs completed around the start of each month in artist leaderboards and stats. store.test.ts mocks db.get/all and only asserts pass-through values, so it never exercises this comparison and cannot catch the bug.

**Location:** `src/features/artJobs/store.ts:449-467, 481-495`
**Category:** data-integrity | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Make the bound match the stored format and timezone. Either compute the boundary with SQLite (e.g. `completed_at >= datetime('now','start of month')`) or format the JS Date as a UTC 'YYYY-MM-DD HH:MM:SS' string (space separator, no ms/Z) using UTC getters. Whichever is chosen, the comparison string and the stored column must use the same format and the same (UTC) timezone.
