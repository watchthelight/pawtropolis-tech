# #00143 -- Level-reward dedup row is committed BEFORE grants succeed, so a transient grant failure permanently skips the 

**Type:** bug | **Priority:** Medium

handleLevelRoleAdded() writes the dedup marker first: `INSERT OR IGNORE INTO level_reward_granted (guild_id,user_id,level)` (lines 130-133). It then loops over rewards calling assignRole() (line 180). I confirmed in src/features/roleAutomation.ts:298-318 that assignRole()'s `member.roles.add()` call is wrapped in try/catch and returns `{success:false, action:'skipped'}` on ANY error (Discord 429 rate-limit, 5xx, network blip) WITHOUT throwing. levelRewards.ts records these in `failedRewards` and logs 'reward_error' (lines 198-209) but never deletes the dedup row. On the next guildMemberUpdate for the same level (the code explicitly notes Amaribot re-syncs and re-joins are normal, lines 268-269), `dedupResult.changes === 0` triggers the early return at line 143, so the previously-failed reward role is never retried. The user permanently loses that reward. A repo-wide grep confirms there is NO DELETE from level_reward_granted anywhere (only the migration backfill + this insert). docs/INCIDENTS.md:57 documents the dedup-first design as the INC-005 TOCTOU fix, but the ordering converts a transient failure into a permanent one - the code carefully distinguishes granted/skipped/failed yet treats all three identically for dedup purposes.

**Location:** `src/features/levelRewards.ts:130-143, 178-229`
**Category:** error-handling / state-consistency | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Only write the dedup marker after a reward is actually granted, OR delete/avoid the dedup row when failedRewards.length>0. Concretely: move the INSERT OR IGNORE to run per-reward after `result.action === 'add'` succeeds, or wrap the dedup-insert + grants in a transaction and `throw` to roll back the marker if any reward returns success:false (so the next event retries). At minimum, on failure execute `DELETE FROM level_reward_granted WHERE guild_id=? AND user_id=? AND level=?` so the failed grant can be retried.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0305. See audit/2026-05-31/full-codebase-audit.md.
