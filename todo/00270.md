# #00270 -- Slow transactions up to 13 s: name the culprit, batch the backfill writer, checkpoint and VACUUM

**Type:** bug | **Priority:** High | **Status:** `WIP`

The current production log window holds 355 `slow_transaction` lines, the slowest at 13,157 ms, and every one of them says `fn: "(anonymous)"` because `db.transaction(() => ...)` callbacks have no name. A 13 s transaction on the bot connection is 13 s of blocked event loop; the likeliest source is the bot waiting in `busy_timeout` while the backfill process commits large batches to the same file.

**Fix**

1. `src/db/db.ts timedTransaction`: capture the caller site when the transaction is created so the log names the file and line.
2. `scripts/backfill/run.ts`: at most 500 rows per transaction and a short yield between batches.
3. After `journal_size_limit` lands, confirm `data.db-wal` shrinks after checkpoints (it is 180 MB today); if not, run `PRAGMA wal_checkpoint(PASSIVE)` from the hourly retention tick and log the result triple.
4. One `VACUUM` in the 6.2.0 release window (44,236 freelist pages, 173 MB).
5. After deploy, rank the labelled `slow_transaction` lines and fix every site above 250 ms or document why it is acceptable.

**Evidence:** `grep -c slow_transaction ~/.pm2/logs/pawtropolis-out.log` = 355 in a 56 MB log; elapsed sample 13157, 11352, 7849, 7460, 6744 ms.
