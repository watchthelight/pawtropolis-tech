# #00065 -- Migration 039 runs on a second DB connection outside the runner's transaction and never records itself (perpet

**Type:** bug | **Priority:** High

Unlike every other migration in the project (which is exported as migrateNNN(db: Database) and receives the runner's connection), migrate039FixArtJobUniqueConstraint() takes NO parameter and instead does `import { db } from "../src/db/db.js"` (line 12), operating on the singleton connection opened by src/db/db.ts. The runner in scripts/migrate.ts (lines 195-213) loads the function via name `migrate039FixArtJobUniqueConstraint`, then runs it inside `db.transaction(() => migrateFn(db))` using ITS OWN better-sqlite3 handle (scripts/migrate.ts line 50). Three concrete consequences: (1) Atomicity is broken. All of 039's writes (the renumber UPDATEs on lines 44-48, DROP INDEX line 53, CREATE UNIQUE INDEX lines 56-59) execute on the singleton connection via autocommit, completely outside the runner's transaction. The runner's transaction stays empty (it issues no writes on its own connection), so if 039 throws partway (e.g. the UNIQUE index creation fails because a duplicate slipped through), the renumber UPDATEs are already committed and will NOT roll back. (2) recordMigration is never called (compare every other migration, e.g. 040 line 135, 038 line 33). The runner does not record versions itself (scripts/migrate.ts applyMigration has no recordMigration call), so version "039" is never inserted into schema_migrations and 039 is treated as pending on every single run -- it re-executes each time `migrate.ts` runs and forces a fresh backup every run (scripts/migrate.ts line 253 filters by appliedVersions which never contains 039). (3) Importing src/db/db.ts from inside the migration process triggers that module's large top-level schema bootstrap (tables + addColumnIfMissing + index creation, src/db/db.ts lines 113-419) to run on a SECOND WAL connection to the same file during the migration -- an unexpected, heavy side effect and a second live handle to the DB the runner is migrating.

**Location:** `migrations/039_fix_art_job_unique_constraint.ts:12-62`
**Category:** correctness | **Confidence:** high | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** Refactor 039 to the standard signature: `export function migrate039FixArtJobUniqueConstraint(db: Database): void` and remove the `import { db } from "../src/db/db.js"`. Use the passed-in `db` for all statements so the work runs inside the runner's transaction. Add `recordMigration(db, "039", "fix_art_job_unique_constraint")` at the end (importing it from ./lib/helpers.js) so the migration is recorded and stops re-running.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0008. See audit/2026-05-31/full-codebase-audit.md.
