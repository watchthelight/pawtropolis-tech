# #00150 -- Audit query 8s timeout is ineffective: Promise.race cannot interrupt synchronous better-sqlite3 work

**Type:** bug | **Priority:** Medium

The audit load wraps cached(key, ...) in Promise.race against a setTimeout(8000) that rejects with 'audit-query-timeout' and maps to a 504 ('Narrow the date range...'). But getAuditLog/getActionTypes run synchronously via better-sqlite3 (db().prepare(...).all/get) and block the Node event loop for their entire duration. While the synchronous query runs, the setTimeout callback cannot fire; by the time control returns to the loop, the cached() promise has already resolved and wins the race. The timeout therefore provides no protection at all: a genuinely heavy audit query (broad FTS search over a large window) freezes the whole web process (all concurrent requests, SSE heartbeats, other tabs) for its full runtime, and the 504 branch is effectively dead code. The load trusts Promise.race to bound work that is fundamentally uninterruptible from JS.

**Location:** `web/src/routes/dashboard/audit/+page.server.ts:49-74 (Promise.race + timeout); queries in web/src/lib/server/queries/audit.ts:55-60 are synchronous better-sqlite3`
**Category:** SSR / event-loop blocking | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Either (a) remove the timeout and bound the work at the SQL/data layer instead (hard LIMITs, mandatory date window, FTS prefix caps, a covering index, or a statement-level progress-handler/interrupt on the better-sqlite3 connection), or (b) move audit queries to a worker_thread so a watchdog timer can actually cancel/abandon them. Do not present a Promise.race timeout as a guard against synchronous DB calls; at minimum drop the misleading 504 path.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0348. See audit/2026-05-31/full-codebase-audit.md.
