# #00269 -- Deploy backups fill the disk: prune data/backups, fix the cleanup script, prune from the bot

**Type:** bug | **Priority:** Critical | **Status:** `WIP`

The production root filesystem is 83% full (51 of 61 GB) and `/home/ubuntu/pawtropolis-tech/data` accounts for 32 GB of it with 41 files in `data/backups`, while the live database is 1.6 GB.

**Cause:** `deploy.sh` writes a pre-deploy copy to `data/backups/data.db.<timestamp>` on every deploy, and `scripts/cleanup-backups.sh` looks for `data.db.backup-*` inside `data/` (the migration runner's naming), so it has never matched a single deploy backup.

**Fix**

1. One manual prune during the 6.2.0 release: keep the 3 newest files in `data/backups`, delete the rest, record `df -h /` before and after.
2. `scripts/cleanup-backups.sh`: default `BACKUP_DIR` to `data/backups` and match `data.db.*`.
3. `src/scheduler/retentionScheduler.ts`: daily backup pruning of `env.DB_BACKUPS_DIR` with the same policy (keep 3 newest plus anything under 7 days), dry-run with candidate counts and bytes until `RETENTION_ENABLED=true`.
4. Health summary shows database file, WAL and freelist sizes so growth is visible.

**Evidence:** `du -sh /home/ubuntu/pawtropolis-tech/data` = 32G; `ls data/backups | wc -l` = 41; `df -h /` = 83%.

## Update 2026-09-01

- `scripts/cleanup-backups.sh` defaults to `data/backups` and matches `data.db.*`.
- `pruneDeployBackups` in `src/scheduler/retentionScheduler.ts` runs on the daily tick: groups each `data.db.<ts>` with its -wal/-shm siblings, keeps the 3 newest groups and anything under 7 days, logs `retention_backups` with candidate count and bytes; deletes only with `RETENTION_ENABLED=true`.
