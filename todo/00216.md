# #00216 -- Default mockAll return value is unreachable; per-action count assertions are vacuous

**Type:** bug | **Priority:** Low

The default mock is `mockAll.mockImplementation((query) => { if (typeof query === "string") return []; return [{action:"approve",cnt:80},{action:"reject",cnt:15},{action:"kick",cnt:5}]; })`. The intent is that the per-action counts query returns the approve/reject/kick array. But in the source (src/commands/stats/history.ts lines 111-118) the counts query is built as `db.prepare(SQL).all(moderator.id, guildId, fromTimestamp)` - the SQL string is the argument to db.prepare(), and the FIRST argument passed to `.all()` is always `moderator.id` (the string "mod-user-123"). The test's withSql mock passes the SQL string as `_sql` and ignores it, invoking `fn()` which calls `.all(moderator.id, ...)`. Therefore the `query` parameter the mock inspects is ALWAYS the actor-id string, so `typeof query === "string"` is ALWAYS true and the mock ALWAYS returns []. The `[{approve:80}...]` branch is dead code. Consequence: in every test using the default beforeEach (e.g. 'embed contains approvals and rejections' L347, 'embed contains reject rate' L361), `counts` is always {} and computed Approvals/Rejections/Reject-Rate values are 0/0.0. Those tests only assert the field NAMES exist (toContainEqual with name only, never value), so they pass regardless and would NOT catch a regression that mis-computes approval/rejection counts or reject rate. This is a false sense of coverage on the command's core numeric output.

**Location:** `tests/commands/stats/history.test.ts:108-115`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Make the mock branch on the SQL text rather than the bound parameters, e.g. set per-call implementations via the prepared SQL: have `mockPrepare.mockImplementation((sql) => ({ get: mockGet, all: (...args) => routeBySql(sql, args) }))` and key the returned rows off `sql` (counts vs response_ms vs daily). Then add value assertions like `expect(fields.find(f=>f.name==="Approvals").value).toBe("80")` so the count math is actually exercised.
