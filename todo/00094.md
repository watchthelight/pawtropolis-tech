# #00094 -- Pulse insights engine runs 18 detectors with ~50 synchronous SQLite queries per request, several non-sargable

**Type:** bug | **Priority:** Medium

getInsights() loops over 18 detector functions sequentially (line 1483). Each detector fires 1-6 synchronous better-sqlite3 queries: e.g. detectMessageAnomaly runs 1 + 4-in-a-loop COUNT(*) over message_activity (lines 827-846), detectCommunicatorRatioDecline runs 2 queries x4 windows = 8 queries (lines 910-926), detectVoiceTrend runs 4, detectAppBacklog/ModWorkloadImbalance/RejectionRateShift each scan review_action via 'app_id IN (SELECT id FROM application WHERE guild_id=?)' semi-joins. Conservatively this is ~40-55 blocking queries on a single SSR request, all on the synchronous DB handle, several aggregating over the million-row message_activity / action_log / review_action tables. Because better-sqlite3 is synchronous (web/src/lib/server/db.ts), the entire Node event loop is blocked for the full duration on every cold cache load, stalling all other concurrent dashboard requests. The page-level cache (CACHE_TTL.medium=60s, pulse/+page.server.ts:37) only masks this between refreshes and per time-window; every distinct window and every 60s expiry pays the full cost.

**Location:** `web/src/lib/server/queries/pulse.ts:1451-1498`
**Category:** perf | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Collapse the per-window repeated COUNT(*) loops (detectMessageAnomaly, detectCommunicatorRatioDecline, detectVoiceTrend) into single GROUP BY queries that return all buckets at once. Share one pass over message_activity / user_activity / review_action across detectors instead of re-querying per detector (pass a small pre-aggregated context into the detectors). Consider precomputing insights in the existing cron rollup (like observatory does) and reading a rollup table at request time.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0283. See audit/2026-05-31/full-codebase-audit.md.
