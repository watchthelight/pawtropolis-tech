# #00200 -- 7-day reopen window miscomputed due to UTC-vs-local Date parsing of closed_at

**Type:** bug | **Priority:** Low

closeTicket() (src/features/modmail/tickets.ts:165) writes closed_at via SQLite datetime('now'), which produces a space-separated UTC string with NO timezone marker, e.g. "2026-05-31 12:00:00". At threadReopen.ts:73 this is parsed with `new Date(ticket.closed_at).getTime()`. Per ECMAScript, a date-time string that uses a space separator and omits a timezone offset is treated as LOCAL time by V8/Node, not UTC. So the computed `closedAt` epoch is shifted by the host's UTC offset (e.g. +7h on a UTC-7 server, making the ticket look ~7h newer; -offset on UTC+ servers, making it look older). The `now - closedAt > sevenDays` boundary at line 77 is therefore wrong by the server's UTC offset, so tickets near the 7-day edge are routed down the wrong branch: some get a brand-new thread when they should reopen the old one, and others reopen an old (possibly already-archived/locked) thread when they should start fresh. The unit tests in tests/features/modmail/threadReopen.test.ts pass only because they feed closed_at via Date.toISOString() (with a 'Z'), which IS parsed as UTC - masking the production format mismatch. The same bug exists in src/features/modmail/dashboardBridge.ts:304 (dashboardReopenThread) and the modstats calc in context/06 docs, so behavior is inconsistent across entry points.

**Location:** `src/features/modmail/threadReopen.ts:73-85`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Parse the stored value as UTC explicitly. Either store an epoch (strftime('%s','now')) and read it as a number, or normalize before parsing: replace the space with 'T' and append 'Z' (e.g. `new Date(ticket.closed_at.replace(' ', 'T') + 'Z')`), or route through the existing normalizeTimestamp helper used in web/src/lib/server/queries/modmail.ts. Apply the same fix in dashboardBridge.ts:304 and update the tests to use the SQLite datetime format ('YYYY-MM-DD HH:MM:SS') so they actually exercise the production path.
