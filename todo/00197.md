# #00197 -- Any gatekeeper can flush/close a batch session owned by a different gatekeeper via the send branch

**Type:** bug | **Priority:** Low

The toggle 'send and close' branch is entered solely when isMemberBuffered(guild.id, target.id) is true (line 118), with no check that the current user opened the session. addMember (the add branch) explicitly guards against cross-opener interference and returns 'denied_other_opener' (welcomeBatch.ts line 204-205), but flushSession has no such owner check. So if gatekeeper A opens a batch and queues user X, gatekeeper B right-clicking the buffered user X will flush and close A's in-progress session prematurely. This is an asymmetric authorization inconsistency: B is blocked from adding to A's session but allowed to send/close it. Impact is limited because all actors are trusted gatekeepers, but it can cause A's batch to be sent before A finished queueing.

**Location:** `src/commands/welcomeBatchContext.ts:118-150`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** In the isMemberBuffered branch, fetch the session opener (getSessionStatus(guild.id).openedBy) and if it differs from interaction.user.id (and the user is not a bypass/owner), reply that another gatekeeper owns the session instead of flushing it.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0065. See audit/2026-05-31/full-codebase-audit.md.
