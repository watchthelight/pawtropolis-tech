# #00083 -- Level-reward dedup marker is written before checking whether any reward exists, permanently blocking rewards a

**Type:** bug | **Priority:** High

handleLevelRoleAdded writes the permanent dedup row INSERT OR IGNORE INTO level_reward_granted (guild_id,user_id,level) at line 130-133, and only AFTERWARD calls getLevelRewards(guild.id, level) at line 146. When a user reaches a level that currently has zero configured rewards, the function still commits the dedup marker, then returns at line 147-154 because rewards.length===0. The dedup table has UNIQUE(guild_id,user_id,level) and is never cleared (migration 057; only roles.ts:538 deletes from level_rewards config, not from level_reward_granted). Consequently, if staff later add a token/ticket reward for that level (a normal economy operation), every user who already passed that level can NEVER receive it: the dedup INSERT OR IGNORE returns changes===0 and the function short-circuits at line 135-143 before getLevelRewards is ever consulted. Cross-file: the reward catalog (level_rewards, edited via roles.ts) and the dedup ledger (level_reward_granted) are decoupled, and the ordering here makes the ledger record a 'granted' fact that never happened.

**Location:** `src/features/levelRewards.ts:130-154`
**Category:** economy/correctness | **Confidence:** high | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** Check getLevelRewards FIRST and return early when there are no rewards, WITHOUT writing the dedup row. Only insert the dedup marker once you have a non-empty reward set to grant (ideally insert it inside the same transaction that performs/records the grants). This preserves idempotency while letting newly-added level rewards reach users who level past that tier afterward.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0317. See audit/2026-05-31/full-codebase-audit.md.
