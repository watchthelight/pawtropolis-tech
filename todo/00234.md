# #00234 -- "allows direct ID routes when enabled" test never exercises the direct-ID path it claims to cover

**Type:** refactor | **Priority:** Low

src/web/badgeEndpoint.ts captures `ALLOW_DIRECT_ID_ROUTES` at module import time (badgeEndpoint.ts l40-42), so setting `process.env.BADGE_ALLOW_DIRECT_DISCORD_ID_ROUTES = 'true'` inside the test (l141) has no effect on the already-loaded module - the test's own comment (l142-145) admits this. The request it then issues, `/badges/movie-tier-1.svg`, is served by `tryServeRegistryBadge` because a matching manifest entry was seeded (l147-148); that branch returns 200 regardless of the direct-ID flag. So the assertion `expect(r.status).toBe(200)` (l151) passes via the registry path, not the direct-ID-enabled path. The genuinely flag-gated code (badgeEndpoint.ts l163-187, the `/badges/(roles|channels|users)/<id>.svg` branch and its enabled behavior) is therefore never tested. Impact: false confidence - a regression that broke direct-ID-route serving when the env flag is on would not be caught by this test.

**Location:** `tests/web/badgeEndpoint.test.ts:140-152`
**Category:** dead-code | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Make the flag injectable so it can be toggled per-test (e.g. read `process.env` at call time inside handleBadgeRequest, or thread an `allowDirectIdRoutes` option through `BadgeStoreConfig`), then assert against a real `/badges/roles/<digits>.svg` request returning a rendered badge (200 + image/svg+xml) when enabled and 404 `direct_id_routes_disabled` when disabled.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0230. See audit/2026-05-31/full-codebase-audit.md.
