# #00075 -- Artist-rotation 'next artist' selection is a check-then-act race (TOCTOU) across /redeemreward issue→confirm a

**Type:** bug | **Priority:** High

getNextArtist(guildId) (redeemreward.ts:192) is a pure SELECT (src/features/artistRotation/queue.ts:264-279) - it does NOT mutate the queue. The selected artistId is baked into the Confirm button customId (redeemreward.ts:283). The queue is only mutated by processAssignment() when Confirm is clicked (src/features/artistRotation/handlers.ts:228). handleConfirm trusts the command-time artistId and never (a) re-checks that this artist is still next, (b) consumes/dedupes confirmId, nor (c) applies any per-button cooldown (the cooldown in src/features/review/handlers/buttonCooldown.ts is review-only). Two realistic triggers: (1) two staff run /redeemreward (no override) before either confirms - getNextArtist returns the SAME artist both times, both confirm, the artist is assigned twice, gets two art jobs (createJob, handlers.ts:258), and processAssignment runs twice; (2) one staff double-clicks the single Confirm button - interactionCreate (src/events/interactionCreate.ts:599-613) dispatches each click as an independent interaction with no in-flight guard, so handleConfirm runs twice, creating two jobs and double-incrementing assignments. processAssignment itself is transactional, but the decision that feeds it is made far earlier, so the transaction does not close the window. Contrast: the byte-token confirm path explicitly added a race mitigation (src/features/byteTokenHandler.ts:353-382) while this path has none.

**Location:** `src/commands/redeemreward.ts:190-199, 283`
**Category:** race | **Confidence:** high | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** Make the assignment idempotent and re-validated at confirm time: (a) persist pending redemptions keyed by confirmId and atomically consume the row inside processAssignment's transaction (reject if already consumed); and/or (b) for non-override flows, re-run getNextArtist INSIDE the same db.transaction() as processAssignment and assign whoever is actually next at confirm time rather than trusting the customId; and (c) add a short per-(user,confirmId) cooldown / disable the button immediately on first click (interaction.update removing components) to swallow double-clicks.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0252. See audit/2026-05-31/full-codebase-audit.md.
