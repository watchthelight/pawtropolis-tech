# #00137 -- resolveApplication failure replies wipe the review card when called after deferUpdate()

**Type:** bug | **Priority:** Medium

resolveApplication() emits its not-found / guild-mismatch feedback with replyOrEdit(interaction, { content: ... }) and no ephemeral flag. It is invoked from the modal handlers (modals.ts) and from the claim/wrong_password/stale_modmail button paths (buttons.ts) AFTER deferUpdate() has run. Because deferred=true, replyOrEdit -> editReply edits the source review card, replacing it with 'No application with code XXXXXX.' publicly and stripping its buttons. This turns a benign 'card references a since-deleted app' situation into destruction of the live card. (When invoked from the modal-opening button paths before any defer it is fine - there it correctly uses reply.)

**Location:** `src/features/review/handlers/helpers.ts:90-125`
**Category:** correctness | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Have resolveApplication detect an already-acknowledged component interaction and use followUp({ flags: Ephemeral }) for its failure messages, or pass a flag from callers indicating whether the interaction was deferUpdate'd so it can choose followUp vs reply.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0268. See audit/2026-05-31/full-codebase-audit.md.
