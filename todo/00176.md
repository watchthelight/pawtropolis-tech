# #00176 -- Review queue layout runs uncached query with ~3 correlated modmail subqueries per application row on every nav

**Type:** bug | **Priority:** Low

getReviewQueue() is invoked from dashboard/reviews/+layout.server.ts:14 with NO caching, so it executes on every page load and every client-side navigation into any /dashboard/reviews/* route (the layout re-runs). The query attaches, per pending application row, two correlated scalar subqueries in the SELECT (has_unread_modmail EXISTS at 404-411, modmail_awaiting_since at 412-419) plus a third correlated EXISTS in the ORDER BY (432-439). Each of those contains a further nested 'SELECT MAX(mm2.id) ... WHERE ticket_id = mt.id' subquery. So the work is roughly 3 x (pending app count) correlated subqueries, each doing a nested aggregate. idx_modmail_message_ticket_id(ticket_id, id DESC) (migration 063) helps the MAX lookups but the per-row fan-out and the ORDER BY recomputation remain. Synchronous handle => blocks event loop per load.

**Location:** `web/src/lib/server/queries/reviews.ts:388-461`
**Category:** perf | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Precompute the 'latest message direction + timestamp per open ticket' once via a single GROUP BY / window-function CTE joined to applications, instead of three correlated subqueries per row (the ORDER BY repeats the same EXISTS a fourth time). Cache the queue with the existing cached() helper (short TTL) since the same payload is recomputed on every reviews navigation.
