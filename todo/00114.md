# #00114 -- 7-day reopen window parses UTC SQLite timestamp as local time

**Type:** bug | **Priority:** Medium

`const closedAt = ticket.closed_at ? new Date(ticket.closed_at).getTime() : 0;` then `if (now - closedAt > sevenDays)`. `closed_at` is written by `closeTicket` as `datetime('now')` (src/features/modmail/tickets.ts:165) and the column is TEXT (src/db/db.ts:187), producing a UTC string like `"2025-05-31 14:00:00"` with no timezone marker. Per V8/Node semantics, `new Date("YYYY-MM-DD HH:MM:SS")` (space-separated, no 'Z') is interpreted in the host's LOCAL timezone, not UTC. Comparing that against `Date.now()` (true UTC epoch) shifts `closedAt` by the host's UTC offset (up to ±14h), so the 7-day boundary is wrong by that offset whenever the bot host is not on UTC - a ticket can be treated as 'too old' (forcing a brand-new thread) or 'still reopenable' incorrectly near the boundary. The codebase already knows the correct fix: src/ui/reviewCard.ts:108-111 and src/features/review/card.ts:129 normalize with `trimmed.replace(' ', 'T') + 'Z'` before parsing; this call site omits it. (Same defect exists in the sibling src/features/modmail/dashboardBridge.ts:304.)

**Location:** `src/features/modmail/threadReopen.ts:73`
**Category:** correctness | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Normalize before parsing, mirroring reviewCard.ts: `const raw = ticket.closed_at; const iso = raw && raw.includes(' ') && !raw.includes('T') ? raw.replace(' ', 'T') + 'Z' : raw; const closedAt = raw ? Date.parse(iso) : 0;` Or store closed_at as a Unix epoch integer (strftime('%s','now')) consistently and compare numerically.
