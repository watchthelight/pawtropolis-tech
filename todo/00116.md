# #00116 -- Reopen 7-day window uses local-time parsing of a UTC SQLite timestamp (timezone-dependent boundary error)

**Type:** bug | **Priority:** Medium

closeTicket() in tickets.ts writes closed_at with SQLite datetime('now'), which produces a UTC wall-clock string WITHOUT a timezone marker, e.g. '2026-05-31 12:00:00' (space-separated, no 'Z'). threadReopen.ts line 73 then does `new Date(ticket.closed_at).getTime()`. V8/Node parses a non-ISO, space-separated date string as LOCAL time, not UTC. So the parsed instant is shifted by the host's UTC offset. The result feeds the 7-day comparison `now - closedAt > sevenDays` (line 77), which decides whether to reopen the existing thread vs. create a brand-new one (line 79). On a host behind UTC the effective window is lengthened; ahead of UTC it is shortened - by up to the full UTC offset (e.g. ~5-8h for US zones). Tickets right at the boundary will take the wrong branch: either spuriously spawning a new thread (and new ticket row) for a ticket that should reopen, or reopening a thread Discord may have already auto-archived. The unit tests mask this because threadReopen.test.ts constructs closed_at via Date.toISOString() (with 'Z', parsed as UTC), which never matches the real datetime('now') format the DB actually stores. dashboardBridge.ts:304 repeats the same `new Date(ticket.closed_at)` pattern on the same column, so the inconsistency is systemic.

**Location:** `src/features/modmail/threadReopen.ts:73-85`
**Category:** correctness | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Parse closed_at as UTC explicitly. Either store epoch seconds (strftime('%s','now')) like open_modmail.created_at and compare numerically, or normalize on read, e.g. `const closedAt = ticket.closed_at ? Date.parse(ticket.closed_at.replace(' ', 'T') + 'Z') : 0;`. Align closeTicket() and the reopen/dashboard readers on one canonical format, and update tests to use the actual DB format.
