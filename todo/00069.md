# #00069 -- ensureGateEntry calls .has() on fetchPins().items which is a plain Array, throwing TypeError after a successfu

**Type:** bug | **Priority:** High

In discord.js 14.26.4 (the pinned version, ^14.26.4), MessageManager.fetchPins() returns `{ hasMore: boolean, items: readonly MessagePin[] }` where `items` is a plain readonly Array (typings/index.d.ts lines 6581-6590). The pin-verification block casts `items` to `{ has: (id) => boolean }` and calls `pinnedItems.has(message.id)`. Arrays have `includes`, not `has`, so `pinnedItems.has` is undefined and the call throws `TypeError: pinnedItems.has is not a function`. This runs INSIDE the try at line 596 AFTER message.pin() has already succeeded; the catch at 615 logs and then re-throws (line 623). ensureGateEntry is awaited inside withStep('ensure_entry', ...) in src/commands/gate/gateMain.ts:214, and withStep propagates (cmdWrap.ts:392, 'caught by wrapCommand upstream'). Net effect: every /gate setup (and /update re-ensure at update.ts:427) that successfully pins the panel still surfaces an error card to the staff user, even though the panel was created and pinned correctly. Note the SAME file's findExistingGateEntry (lines 160-167) correctly treats items as an array of {message}, proving the intended shape.

**Location:** `src/features/gate/entryPanel.ts:600-607`
**Category:** correctness | **Confidence:** high | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** Replace the Collection-style `.has()` access with array semantics consistent with the rest of the file: `const pinnedItems = (pinnedResponse as { items?: ReadonlyArray<{ message?: Message }> }).items; const pinnedMatch = Array.isArray(pinnedItems) ? pinnedItems.some((it) => it?.message?.id === message.id) : false;`. Then the success path returns result without throwing.
