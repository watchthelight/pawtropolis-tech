# #00161 -- SILENT_FIRST_MSG_DAYS env var silently overrides a guild's explicit DB value of 7

**Type:** bug | **Priority:** Low

getFlaggerConfig initializes silentDays=7, then reads the DB row. If the DB has a non-null silent_first_msg_days it is assigned to silentDays (lines 140-142). The env fallback at line 166 only fires when `silentDays === 7`. The problem: 7 is a VALID, user-settable value (setSilentFirstMsgDays accepts days>=7, line 236). So a guild that deliberately ran `/config set flags.silent_days 7` stores 7 in the DB, but on read the code cannot distinguish "DB said 7" from "DB had no row / null", and therefore overwrites the guild's explicit 7 with the env default (e.g. SILENT_FIRST_MSG_DAYS=60). This violates the documented resolution priority (DB > ENV, lines 102-106) for exactly the value 7. Impact: a guild that intentionally set the most-aggressive 7-day threshold gets a different (env) threshold applied to first-message flagging, changing who gets flagged. The in-code comment even acknowledges the brittleness ('GOTCHA: This logic assumes 7 is the default').

**Location:** `src/config/flaggerStore.ts:165-170`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Track whether the DB actually supplied a value instead of overloading the sentinel 7. e.g. `let dbProvidedDays = false;` set true inside the `row.silent_first_msg_days !== null` branch, then gate the env fallback on `!dbProvidedDays` instead of `silentDays === 7`.
