# #00196 -- handleHelpButton switch has no case for the 'search' navigation type and no button ever emits a search nonce i

**Type:** refactor | **Priority:** Low

parseHelpCustomId can return { type: 'search', nonce } for ids matching /^help:search:([a-f0-9]+)$/ (metadata.ts:257-264), but buildHelpCustomId({ type:'search' }) is never called anywhere in src (only the type union and the builder case exist). Search results are navigated via the select menu id `help:select:search:${nonce}` (components.ts:260), which is routed to handleHelpSelectMenu, not through a button. Consequently: (1) no button ever produces `help:search:<nonce>`, and (2) even if one did, handleHelpButton's switch (lines 326-343) has cases only for overview/category/command/search_modal, so 'search' would hit `default` and reply 'Unknown navigation'. This is dead/unreachable code rather than a live bug; flagged for cleanup and to document the gap should a future change start emitting search-nonce buttons.

**Location:** `src/commands/help/index.ts:326-349`
**Category:** dead-code | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Either remove the unused 'search' member from HelpNavigation + its builder/parser branches, or add a `case 'search':` that loads the session via getSearchSession(nav.nonce) and re-renders results, if button-based search navigation is intended.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0052. See audit/2026-05-31/full-codebase-audit.md.
