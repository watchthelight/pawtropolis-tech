# #00062 -- Byte token redemption is non-atomic and has no rollback - a failed grant destroys the token entitlement with n

**Type:** bug | **Priority:** Critical

handleConfirm() mutates Discord and the DB in this order inside one try/catch with no compensating action: (1) remove the token role (line 314), (2) remove other multiplier roles (lines 321-345), (3) add the multiplier role (line 348), (3.5) refetch + cleanup (lines 357-382), (4) upsertActiveMultiplier writes the DB source-of-truth (lines 385-394). If ANY step after the token removal throws (e.g. roles.add at 348 hits a 50013/permission change, a 429, or the gateway hiccups), control jumps to the catch at 449 which only shows an error embed. The token role is already gone, the multiplier role was never granted, and NO row was written to active_byte_multipliers. The user has permanently spent a finite token entitlement and received zero value, with no automatic recovery path (the scheduler only removes roles; nothing re-grants tokens). Because the multiplier roles ARE the economy (see byteMultiplierStore multiplier_value is never read - XP boost is driven purely by role possession), this is direct, silent value destruction. The DB write should be the authoritative claim and should happen first/atomically, or the whole sequence must be made compensatable.

**Location:** `src/features/byteTokenHandler.ts:312-468`
**Category:** correctness | **Confidence:** high | **Audit severity:** critical (adversarially confirmed)

**Suggested fix:** Make the token claim the atomic gate before any irreversible Discord mutation. Insert into a redeemed-tokens ledger (or upsert active_byte_multipliers) inside a transaction FIRST; only on a successful insert proceed to Discord role changes. On any Discord failure after the token role is removed, re-add the token role in a finally/catch (compensating action) and delete the just-written DB row, so the user keeps their token. Alternatively, add the multiplier role BEFORE removing the token role, so a mid-flight failure leaves the user holding the token (recoverable) rather than holding nothing.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0261. See audit/2026-05-31/full-codebase-audit.md.
