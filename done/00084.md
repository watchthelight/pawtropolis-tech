# #00084 -- Art-ticket redemption (/redeemreward) trusts a stale role snapshot captured at command time and the only spend

**Type:** bug | **Priority:** High

redeemreward.ts builds the confirmation when staff invokes the command, encoding recipientId+artType into the button customId (line 283). The actual debit happens later in handlers.ts handleConfirm: after deferUpdate (line 120) it fetches the member and removes the ticket role only if member.roles.cache.has(ticketRoleId) (line 131-134). There is no DB-backed entitlement for art tickets in the redeem path - the Discord ticket role IS the single-use token (see redeemreward.ts comment line 81-83 'we remove the role so they can't double-dip'). Because the has()-check + remove() is a check-then-act on the eventually-consistent cache with no transactional claim, two confirmations for the same recipient+type (e.g., staff double-clicks, or two staff each run /redeemreward for the same person before either confirms) can both observe the role present, both 'succeed', and produce TWO assignments + TWO art_job rows (createJob, line 258) while only one ticket existed. The branch at line 135-137 ('User did not have ticket role') still proceeds to assign an artist and create a job, so even a redemption against a user with NO ticket is logged as a successful assignment with only a soft warning embed. This is the spend half of the same economy whose grant half is patreon_art_granted; neither side reconciles against the other.

**Location:** `src/features/artistRotation/handlers.ts:120-145, 224-242`
**Category:** economy/race | **Confidence:** medium | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** Tie the spend to an atomic DB claim instead of (or in addition to) the Discord role: in handleConfirm, perform a conditional decrement/claim against a per-user art-ticket ledger inside a transaction and abort if nothing was claimed. At minimum, hard-fail (do not create a job or rotate the artist) when the recipient does not actually hold the ticket role, and de-duplicate concurrent confirms with a per-(recipient,artType) guard.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0318. See audit/2026-05-31/full-codebase-audit.md.
