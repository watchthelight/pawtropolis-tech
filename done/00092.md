# #00092 -- verified_users row is inserted BEFORE the role grant; grant failure leaves a verified record with no role and 

**Type:** bug | **Priority:** Medium

The flow inserts into verified_users first (lines 196-198), then attempts member.roles.add (lines 206-217) inside a try/catch that ONLY logs on failure (logger.error at 216) and continues. If the role add fails (missing Manage Roles permission, role above the bot in hierarchy, transient API error, member fetch failure), the user is permanently recorded as verified in the DB but never receives the Thin Line role. The log embed is still sent with 'Role Granted: Failed', but the user is told 'Thank you for your service. You have been given the Thin Line role.' (line 219) regardless. Worse, if they re-run /verify, the existence check at lines 69-81 finds the row and replies 'You're already verified ... You have the Thin Line role.' so they can never recover the role through the command. The write is non-idempotent w.r.t. the actual desired state (DB row + role).

**Location:** `src/commands/verify.ts:196-217`
**Category:** data-integrity | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Grant the role first (and treat a failed grant as a hard failure that aborts before the INSERT), or wrap both in a compensating flow: if roles.add throws, do not insert (or delete the just-inserted row) and tell the user verification could not be completed. At minimum, make the success DM and embed conditional on roleGranted, and make the 'already verified' path re-attempt the role grant if the member lacks the role.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0054. See audit/2026-05-31/full-codebase-audit.md.
