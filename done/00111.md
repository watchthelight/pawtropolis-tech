# #00111 -- closeModmailThread / closeModmailForApplication are check-then-act with no atomic guard: concurrent close (dou

**Type:** bug | **Priority:** Medium

closeModmailThread guards only with a plain read: getTicketById then `if (ticket.status === 'closed') return` (lines 211-228). Two near-simultaneous invocations (e.g. a fast double-click of the Close button - handleModmailCloseButton at handlers.ts:144-159 calls deferUpdate then closeModmailThread, and Discord delivers two distinct interactions; OR a moderator clicking Close while an approve/reject decision concurrently runs closeModmailForApplication, which is fired unawaited via .catch() from web/routes/review.ts:223-608 and review/handlers/actionRunners.ts) both read status='open', both pass the guard, and both proceed. flushTranscript is NOT idempotent: the first call posts the transcript and deletes the in-memory buffer (transcript.ts:262); the second call finds an empty buffer, reconstructs the same conversation from modmail_message in the DB (transcript.ts:129-160), and posts a SECOND transcript message to the log channel. The user also receives two 'Modmail Closed' DMs, the dashboard gets two thread_closed notifications, and two modmail_close action-log rows are written. closeModmailForApplication has the same plain-read guard (getOpenTicketByUser at lines 456-460) and shares no lock with closeModmailThread, so the two functions can race each other as well.

**Location:** `src/features/modmail/threadClose.ts:202-307`
**Category:** race | **Confidence:** medium | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Make the status flip the atomic gate. Perform the close inside a transaction that conditionally updates only when still open and checks the affected row count, e.g. `UPDATE modmail_ticket SET status='closed', closed_at=datetime('now') WHERE id=? AND status='open'`; if changes()===0, another path already closed it - return early and skip transcript flush, DM, archive, logging, and dashboard notify. Apply the same guarded UPDATE in both closeModmailThread and closeModmailForApplication so they mutually exclude.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0089. See audit/2026-05-31/full-codebase-audit.md.
