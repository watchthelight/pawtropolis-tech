# #00142 -- ensureReviewMessage check-then-create race posts duplicate review cards (and double Gatekeeper ping) under con

**Type:** bug | **Priority:** Medium

ensureReviewMessage reads the existing review_card mapping once near the top (lines 799-801) and then decides create-vs-edit based on that snapshot. The decision and the create are separated by many awaits (embed render via inSpan at 837-851, several dynamic imports). On the no-mapping path it does `await channel.send(...)` to post a brand-new card (lines 919-929, including a one-time Gatekeeper/bot-dev role ping) and only writes the review_card row at the very end (upsert at line 958, after the send). If two callers invoke ensureReviewMessage for the same appId while no card exists yet, both read mapping===undefined, both fall into the create branch, both channel.send a card, and the second upsert (review_card.app_id is PRIMARY KEY, db.ts:127-135) either throws a PRIMARY KEY constraint or overwrites -- but two physical Discord messages have already been posted with duplicate role pings, and only one survives in the mapping table (the orphan keeps live buttons). This concurrent no-mapping window is real and acknowledged in-tree: src/features/gate/scan.ts:66-102 added waitForReviewCardMapping() specifically because the avatar-scan job (fired via setImmediate on submit) calls ensureReviewMessage concurrently with the submit handler's own ensureReviewMessage. That poller is only a mitigation with a 5s timeout, and scan.ts:210-217 explicitly calls ensureReviewMessage even when the wait times out (cardReady===false), so a slow initial card-create re-opens the double-post window. ensureReviewMessage has no internal mutex; the comment at scan.ts:71-73 admits 'Polling is simpler than adding cross-module eventing.'

**Location:** `src/features/review/card.ts:799-959`
**Category:** Concurrency / check-then-act on shared external state | **Confidence:** medium | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Make card creation atomic against the PRIMARY KEY instead of relying on a pre-read snapshot. Move the channel.send into a flow like modmail threadOpen: first INSERT a placeholder review_card row (INSERT ... ON CONFLICT DO NOTHING) to claim ownership; only the caller whose INSERT changed a row proceeds to channel.send and then UPDATEs with the real message_id; losers re-read the mapping and edit instead. Alternatively serialize ensureReviewMessage per-appId with an in-process promise chain keyed by appId (as inviteTracker.ts does with trackingQueue). At minimum, re-query the mapping immediately before the create branch (after all awaits) and switch to edit if a row now exists.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0300. See audit/2026-05-31/full-codebase-audit.md.
