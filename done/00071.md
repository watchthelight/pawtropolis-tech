# #00071 -- BigInt() called on comma-separated permission NAMES, not numeric bitfields - diff/dangerous-change code throws

**Type:** bug | **Priority:** High

Every consumer in this file treats RoleSnapshot.permissions and PermissionOverwriteSnapshot.allow/deny as numeric bitfield strings: `new PermissionsBitField(BigInt(oldRole.permissions))` (256-257), `BigInt(oldOw.allow/deny)` (346-349), `BigInt(bitfield)` in bitfieldToPermissionNames (382), and `BigInt(role.permissions)` in getDangerousChanges (414). But the ONLY producers of those fields are roleToSnapshot/channelToSnapshot in src/features/serverAudit/types.ts (lines 234, 252-253), which store comma-separated permission NAMES: `permissions: role.permissions.join(',')` and `allow/deny: ow.allow.join(',')`. At runtime a snapshot holds e.g. `"Administrator,ManageRoles"` or `"ViewChannel"`. `BigInt("ViewChannel")` throws `SyntaxError: Cannot convert ViewChannel to a BigInt`. Trigger paths: (a) computeSnapshotDiff itself calls getDangerousChanges(diff) at line 247, so it throws whenever diff.rolesAdded is non-empty (any role added since last audit has ≥1 perm) or whenever computeRoleChange runs for a role whose permissions string changed; (b) computeOverwriteModification throws whenever a channel overwrite's allow/deny string changes. Impact: In src/commands/audit/diff.ts the catch at line 141 surfaces `❌ Failed to compute diff: Cannot convert ... to a BigInt` to the user - `/audit diff` is broken for any server with real permission changes. In src/features/serverAuditDocs.ts the whole block is wrapped in a silent try/catch (line 174), so DIFF.md is never written and result.dangerousChangeCount stays 0 - dangerous permission escalations (Admin/ManageRoles/Ban added to a role) are silently never detected or alerted, a security-monitoring failure. The unit test masks this because tests/features/securityDiff.test.ts only ever uses `permissions: "0"` / `""` (BigInt("0")=0n, BigInt("")=0n do not throw) and never diffs two roles that actually differ in a named permission.

**Location:** `src/features/securityDiff.ts:256-257, 346-349, 382, 414`
**Category:** correctness | **Confidence:** high | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** Make producers and consumers agree on one format. Simplest: since snapshots already store comma-separated names, replace the BigInt/PermissionsBitField parsing with set-diffing of the name lists, e.g. `const oldSet = new Set(oldRole.permissions ? oldRole.permissions.split(',') : []);` then compute added = newSet items not in oldSet and removed = oldSet items not in newSet. Do the same for allow/deny in computeOverwriteModification and overwritesAdded/removed, and make bitfieldToPermissionNames just `bitfield ? bitfield.split(',') : []`. Alternatively change roleToSnapshot/channelToSnapshot to store the real numeric bitfield (role.permissions.bitfield.toString()) - but that requires re-fetching bitfields in analyze.ts (RoleData.permissions is already names-only), so the split-based fix is safer. Add a test where two roles differ by a named permission to prevent regression.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0107. See audit/2026-05-31/full-codebase-audit.md.
