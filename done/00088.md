# #00088 -- Documented rollback script deploy-no-tests.sh has no deploy lock and no pre-deploy backup, yet runs migrations

**Type:** bug | **Priority:** High

docs/operations/DEPLOY-AGENT.md documents the rollback procedure as `git checkout HEAD~1 && ./deploy-no-tests.sh` (DEPLOY-AGENT.md:79,125,131). deploy-no-tests.sh runs the migration step (line 25, with the same `|| echo` swallow as the root script) and `pm2 startOrRestart` but: (1) it never acquires the DEPLOY_LOCK_DIR mkdir lock that root deploy.sh uses, so it can race a concurrent `./deploy.sh` and both will scp/extract/restart simultaneously, corrupting the extract or the live WAL; (2) it takes no pre-deploy DB backup (no maybe_backup_remote_db, no Litestream check). Worse, in the documented rollback flow the code is rolled back to HEAD~1 but migrations are still applied FORWARD (the runner only goes forward and tracks via schema_migrations), so you end up with old code on a newer-or-equal schema with zero fresh backup right when you are already in an incident. A rollback path is exactly when you most need the lock and the backup.

**Location:** `C:/Users/Claude-Code/pawtropolis-tech/deploy-no-tests.sh:1-42`
**Category:** deploy-safety/no-lock-no-backup | **Confidence:** high | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** Make deploy-no-tests.sh call `acquire_deploy_lock` and `maybe_backup_remote_db` (or just `BACKUP_BEFORE_DEPLOY=1 ./deploy.sh --fast`). Update DEPLOY-AGENT.md so the rollback recipe uses the hardened script with a forced backup, and note that migrations are not auto-reverted on a code rollback.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0353. See audit/2026-05-31/full-codebase-audit.md.
