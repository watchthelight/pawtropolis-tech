# #00170 -- Scheduler deletes the multiplier DB row even when panic mode blocks role removal, and SELECT-then-DELETE is no

**Type:** bug | **Priority:** Low

cleanupExpiredMultipliers calls removeExpiredMultipliers() (store line 37) which SELECTs all expired rows and then DELETEs them (byteMultiplierStore.ts:182-204) as two separate statements, not inside a db.transaction. The scheduler runs an immediate startup pass (lines 197-207) AND a periodic interval (lines 210-218); if the startup pass is still awaiting Discord REST when the first interval fires (or any tick runs long), a second invocation can SELECT the same not-yet-deleted rows and process them twice - double-removing roles and double-logging byte_multiplier_expired to the audit trail. Separately, processExpiredMultiplier returns early under panic mode (lines 100-109) AFTER the row has already been deleted from the DB, so the multiplier role is left on the member with no tracking row; when panic clears, nothing will ever remove it (the comment at 105-108 acknowledges this requires manual cleanup). Both issues stem from deleting the authoritative row before the side effect that the row exists to drive is confirmed.

**Location:** `src/scheduler/byteMultiplierScheduler.ts:35-109`
**Category:** race | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Wrap the SELECT+DELETE in a single db.transaction so a batch is claimed atomically (better-sqlite3 transactions are synchronous/ACID), and guard cleanupExpiredMultipliers with a reentrancy lock so overlapping ticks can't both run. For panic mode, check isPanicMode BEFORE deleting the row (or re-insert the row when skipping due to panic) so expired-but-unremoved multipliers are retried after panic clears instead of being orphaned.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0264. See audit/2026-05-31/full-codebase-audit.md.
