# #00128 -- actionRunners.test.ts never imports or invokes the action runners it claims to test (vacuous coverage)

**Type:** refactor | **Priority:** Medium

The file is titled 'Unit tests for review action runner functions' and contains describe blocks named runApproveAction/runRejectAction/runPermRejectAction/runKickAction, but it never imports actionRunners.ts and never calls runApproveAction/runRejectAction/runPermRejectAction/runKickAction (grep confirms these names appear only inside describe() strings). Every 'it' asserts against a locally re-implemented literal, e.g. line 161 `const feature = ["review","approve"]; expect(feature).toContain("review")`, line 219 `expect(Object.values(conditions).every(Boolean)).toBe(true)`, line 264 a hand-written roleNote string. The only real imports (approveTx/rejectTx/kickTx from flows/index.js, getClaim/claimGuard) are mocked and then the mocks are called directly (e.g. line 124 `approveTx(...)` returns the mock). Impact: the critical moderation orchestration in actionRunners.ts -- claim-guard enforcement (lines 75-82), the 'role grant failed -> abort approval, do NOT send welcome DM' BLOCK (actionRunners.ts:128-149), modmail auto-close ordering, dmDelivered/roleApplied meta writes, and the duplicate ensureReviewMessage refresh -- has ZERO behavioral coverage from this file while the file name implies it is covered. A regression in any of those paths (e.g. removing the role-grant block, letting an unclaimed mod approve) would not fail a single assertion here. The divergence is concrete: line 124/151 mock approveTx to return {kind:"ok"}, but the real TxResult union (src/features/review/types.ts:132-136) has no "ok" kind (success is "changed"), showing the test was written against a misremembered contract.

**Location:** `tests/features/review/handlers/actionRunners.test.ts:85-617`
**Category:** dead-code | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Import the real runners and drive them with the existing discord.js/db mocks (the sibling approve.test.ts shows the pattern). Assert on the mocked collaborators: that replyOrEdit gets the claim-guard string when claimGuard returns non-null, that channel.send + updateReviewActionMeta({roleApplied:false,dmDelivered:false}) fire and deliverApprovalDm is NOT called when accepted_role_id is set but roleApplied is false, etc. At minimum delete the literal-only assertions so they stop counting toward the coverage gate and misrepresenting coverage.
