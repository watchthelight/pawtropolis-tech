# #00163 -- 7-day reopen window mis-computed due to local-time parsing of UTC SQLite timestamp

**Type:** bug | **Priority:** Low

`ticket.closed_at` is stored by closeTicket() (src/features/modmail/tickets.ts:165) as SQLite `datetime('now')`, i.e. a UTC string of the form "YYYY-MM-DD HH:MM:SS" with no timezone marker (confirmed by schema src/db/db.ts:186-187: `closed_at TEXT`). Line 73 does `new Date(ticket.closed_at).getTime()`. V8 parses the space-separated, marker-less format as LOCAL time, not UTC. Verified empirically: on a UTC-5 host, `new Date('2026-05-31 12:00:00').toISOString()` === '2026-05-31T17:00:00Z' - a 5-hour error equal to the host's UTC offset. Effect: `now - closedAt` is off by the host offset, so the `> sevenDays` boundary at line 77 is wrong by that offset. On a host behind UTC the reopen window is effectively lengthened; on a host ahead of UTC it is shortened, so a ticket closed ~6d 16h ago (with a +9h offset) can be wrongly treated as >7 days and routed to create a brand-new thread (line 79) instead of reopening. The bot is not guaranteed to run in UTC, so this changes user-visible behavior at the boundary.

**Location:** `src/features/modmail/threadReopen.ts:73-85`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Parse as UTC. Either append 'Z'/replace space with 'T'+'Z' (`new Date(ticket.closed_at.replace(' ','T')+'Z')`), or better, store/compare epoch seconds consistently (e.g. compare via SQLite `strftime('%s',closed_at)` or use the project's nowUtc/time helpers). Apply the same parsing fix anywhere closed_at/created_at TEXT columns are turned into Date().
