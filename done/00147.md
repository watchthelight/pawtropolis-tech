# #00147 -- Legendary and Epic tokens map to the same multiplier role and value, so the single-row tracking model lets a c

**Type:** bug | **Priority:** Medium

BYTE_TOKEN_CONFIG.epic and .legendary share multiplierRoleId '1405369052829974543' and multiplierValue 5, differing only in durationHours (48 vs 72). active_byte_multipliers enforces UNIQUE(guild_id,user_id) (migration 044 line 87), so a user can hold only one tracked multiplier. If a user redeems Legendary (role X, 72h) and later redeems Epic while X is still active, byteTokenHandler upsert overwrites expires_at to now+48h (byteMultiplierStore.ts line 71-78) - the consumed Epic token strictly shortens their remaining boost. The confirmation UI's replace-warning (usebyte.ts line 224-231 / byteTokenHandler.ts line 568-574) shows both as '[5x] Byte'/5x, so the user sees no indication they are trading down. Net effect: a redeemed token can be wasted (or actively reduce value) with no surfaced downside, and the two rarities can never be 'active simultaneously' despite being distinct entitlements.

**Location:** `src/commands/usebyte.ts:84-110`
**Category:** economy/correctness | **Confidence:** medium | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Either give legendary its own multiplier role, or, before overwriting, compare expiries and keep the longer-lived boost (only extend, never shorten, when the incoming multiplierValue is equal). Make the replace-warning show actual remaining time vs proposed time so users can see a downgrade. Confirm with product whether legendary collapsing into the epic role is intended.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0321. See audit/2026-05-31/full-codebase-audit.md.
