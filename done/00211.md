# #00211 -- claimedAtToDate/claimedAtToEpoch mis-parse the actual stored claimed_at format (epoch-seconds string) -> Inval

**Type:** bug | **Priority:** Low

These helpers do `new Date(claimed_at)` and `new Date(claimed_at).getTime()/1000`, and their JSDoc/param type declare claimed_at as an "ISO timestamp string". But the value is never ISO: review_claim.claimed_at is a TEXT column (src/db/db.ts:132) and claimTx (src/features/reviewActions.ts:114) inserts nowUtc(), which returns epoch SECONDS as a number (src/lib/time.ts:34 `Math.floor(Date.now()/1000)`). SQLite stores that as a numeric string like "1748600000". `new Date("1748600000")` yields Invalid Date, so claimedAtToDate returns Invalid Date and claimedAtToEpoch returns NaN. The real card consumer sidesteps them with a custom parser (src/ui/reviewCard.ts parseClaimedAt, which explicitly notes the DB "may contain numeric strings from nowUtc()"). A grep shows claimedAtToEpoch/claimedAtToDate are defined but never called anywhere in src/tests/web, so today this is dead code -- but it is a latent trap: any future caller trusting the JSDoc ("ISO timestamp string") will silently get NaN/Invalid Date for every claim.

**Location:** `src/features/review/types.ts:74-85`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Make the helpers tolerant of epoch-seconds numeric strings (and epoch ms), e.g. detect an all-digit string and treat it as seconds: `const n = Number(claimed_at); const ms = Number.isFinite(n) ? (n < 1e12 ? n*1000 : n) : Date.parse(claimed_at); return new Date(ms);`. Alternatively delete the unused helpers and standardize on parseClaimedAt. Also correct the ReviewClaimRow.claimed_at type/comment which claims ISO but is actually an epoch-seconds string.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0158. See audit/2026-05-31/full-codebase-audit.md.
