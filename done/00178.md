# #00178 -- Standalone migration 046 records into a different bookkeeping table than the migration framework

**Type:** bug | **Priority:** Low

The canonical migration tracker is schema_migrations (scripts/migrate.ts:71-78 and migrations/lib/helpers.ts:149-213 via recordMigration). migrations/046_extend_user_cache_profile.ts:32 correctly calls recordMigration(db, '046', ...) which writes to schema_migrations. But the hand-run helper scripts/run-migration-046.mjs:24-27 writes to a separate `migration_log` table instead. Its filename invites manual use during incident response; if an operator runs it, the ALTERs are applied but schema_migrations is NOT updated, so the next deploy's migrate.ts sees 046 as pending and re-runs migrations/046_*.ts. The 046 migration guards each ALTER with columnExists, so the re-run is non-destructive today, but the divergence is a latent footgun: any future standalone fix script following this pattern for a non-idempotent migration would double-apply.

**Location:** `scripts/run-migration-046.mjs:24-28`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Make run-migration-046.mjs either call into the same recordMigration logic (write to schema_migrations) or, better, delete it in favor of `npm run migrate`. At minimum, stamp schema_migrations, not migration_log, so the two paths agree.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0294. See audit/2026-05-31/full-codebase-audit.md.
