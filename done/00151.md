# #00151 -- Pre-deploy DB backup copies a live WAL-mode DB without a checkpoint and misreports any cp failure as 'not foun

**Type:** bug | **Priority:** Medium

maybe_backup_remote_db does `cp ${REMOTE_PATH}/data/data.db .../data.db.${ts} 2>/dev/null && echo OK || echo 'WARNING: data.db not found'`. Two problems. (1) No WAL checkpoint before the copy: the DB runs in WAL mode (ecosystem starts the bot which opens WAL; migrate.ts also sets journal_mode=WAL), so a bare `cp` of just data.db can capture a state missing the committed pages still sitting in data.db-wal, yielding a stale or torn backup. Note the OTHER ops paths get this right: scripts/switch.sh:93 and scripts/start.sh:275,313 run `PRAGMA wal_checkpoint(PASSIVE)` before copying and also copy -wal/-shm. deploy.sh's backup path is the inconsistent, less-safe sibling. (2) The `2>/dev/null && ... || echo 'data.db not found'` collapses every failure mode (disk full, permission denied, I/O error) into the single misleading message 'data.db not found, skipping backup', and because maybe_backup_remote_db always `return`s success, the deploy proceeds to run destructive migrations (035 DROP TABLE) with no valid backup. This directly undermines the stated guarantee 'a botched migration can be reverted by hand' (deploy.sh:122).

**Location:** `C:/Users/Claude-Code/pawtropolis-tech/deploy.sh:127-133`
**Category:** deploy-safety/backup-integrity | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Before copying, run `sqlite3 ${DB} 'PRAGMA wal_checkpoint(TRUNCATE);'` (or copy data.db plus -wal/-shm), mirroring switch.sh/start.sh. Distinguish 'file absent' from 'copy failed': test `[ -f data.db ]` first, and on a real cp failure abort the deploy (return non-zero) instead of printing a benign-sounding warning and continuing into destructive migrations.
