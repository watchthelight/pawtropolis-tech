# #00175 -- detectNsfwFlagSurge and detectModmailResponseTime use strftime() on TEXT timestamp columns, forcing full scans

**Type:** bug | **Priority:** Low

detectNsfwFlagSurge filters nsfw_flags with strftime('%s', flagged_at) >= ? (lines 1216,1222). nsfw_flags.flagged_at is TEXT (migration 032_nsfw_flags.ts:45) and the only indexes are (guild_id) and (guild_id, reviewed) (migration 032:53-54). Wrapping the column in strftime() makes the predicate non-sargable, so SQLite cannot use any time index and scans every flag row for the guild twice (this-window + prev-window). detectModmailResponseTime has the same problem: it computes strftime('%s', mt.created_at) in both the WHERE and via correlated MIN per ticket (lines 1176-1180), defeating any index on modmail_ticket. On servers with large flag/modmail history this is a repeated full/partial scan on the SSR path.

**Location:** `web/src/lib/server/queries/pulse.ts:1215-1226, 1174-1188`
**Category:** sql | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Store/compare timestamps as INTEGER unix seconds (as action_log/message_activity already do) or add a generated/stored *_s column with an index, then filter with plain range comparisons (flagged_at_s >= ? AND flagged_at_s < ?). At minimum add an index on the raw text column and compare against ISO string literals (datetime(?, 'unixepoch')) so the index can be used instead of strftime per row.
