# #00103 -- Resume path bypasses cooldown with no concurrency guard - concurrent resumes double-flag members and double-co

**Type:** bug | **Priority:** Medium

runMembersAudit (and the parallel runNsfwAudit) are launched fire-and-forget from buttonRouter.handleAuditButton, which explicitly skips the per-guild cooldown for action === 'resume' (buttonRouter.ts:128). getActiveSession returns the same in_progress session for every clicker, and nothing marks the session as 'running' or takes a lock. If two staff click Resume on the same prompt (or the same user double-clicks before the message updates), two runners execute against the same sessionId concurrently. markUserScanned uses INSERT OR IGNORE so the scanned-set dedups, but both runners load `alreadyScanned` at start, so members not yet recorded get analyzed by BOTH runners: upsertManualFlag/upsertNsfwFlag fire twice, two flag embeds are sent to the channel, and updateProgress overwrites flagged_count from two racing counters (last-writer-wins, can under- or over-count). For NSFW this also doubles paid Google Vision API calls. Same shape in nsfw.ts:144-243.

**Location:** `src/commands/audit/members.ts:116-174`
**Category:** race | **Confidence:** medium | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Add a lightweight in-process lock keyed by `${guildId}:${auditType}` (or sessionId) that rejects a second concurrent runner, and/or transition the session to a distinct 'running' status when a runner picks it up and refuse to resume a session already being processed. Re-applying the cooldown on resume (with clear-on-complete) would also prevent the double-click case.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0035. See audit/2026-05-31/full-codebase-audit.md.
