# #00154 -- Prod migration step runs `npx tsx`, auto-downloading an unpinned build tool against the live DB

**Type:** chore | **Priority:** Medium

deploy.sh:435 runs `node scripts/migrate-remote.js` on the production host (via ssh_remote), and migrate-remote.js:18 does `spawnSync('npx', ['tsx', 'scripts/migrate.ts', ...], { shell: true })`. tsx is a devDependency (package.json:90; package-lock.json:7940-7944 has `"dev": true`), so the prod install via `npm ci --omit=dev` (deploy.sh:341/421/428) excludes it from node_modules. When `npx tsx` runs and tsx is not locally installed, npx fetches it from the registry on demand. The deploy ssh invocation is non-interactive (no TTY), so npx skips its 'Ok to proceed?' prompt and installs automatically. Net effect: every production migration downloads tsx (and its transitive deps) fresh from npm at an unpinned latest-matching version and executes it with full access to the production SQLite database. A compromised tsx release (or a registry MITM) would run arbitrary code on the DB host during migration. This is distinct from CI, where `npx tsx` (ci.yml:54) runs only after `npm ci` has already installed tsx locally.

**Location:** `scripts/migrate-remote.js:18 (invoked by deploy.sh:435; tsx classified dev-only in package.json:90 / package-lock.json:7944)`
**Category:** Dependency / supply-chain | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Make tsx available deterministically on prod for the migration path: either move tsx to dependencies, or compile the migration runner to plain JS in `dist` and invoke `node dist/.../migrate.js` so no runtime TypeScript loader is needed, or pin the exact tsx version with `npx -p tsx@<pinned> tsx ...` after verifying it is installed from the lockfile. Avoid bare `npx <tool>` on the production host.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0359. See audit/2026-05-31/full-codebase-audit.md.
