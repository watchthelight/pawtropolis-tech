# #00101 -- SQLite datetime strings parsed as local time, producing wrong relative timestamps and day counts

**Type:** bug | **Priority:** Medium

art_job.assigned_at / completed_at are stored as SQLite TEXT via `datetime('now')` (confirmed in src/db/db.ts:353-355 and types.ts:36-39), which yields UTC strings of the form 'YYYY-MM-DD HH:MM:SS' (space separator, no timezone). art.ts feeds these directly into `new Date(job.assigned_at).getTime()` (and the same for completed_at) at lines 425, 635, 712, 732, 865, 1038. Per ECMAScript, a date-time string with a space separator and no offset is parsed in the host's LOCAL timezone by V8/Node, not UTC. So on any host not in UTC, every `<t:...:R>` 'Assigned X ago' value rendered by /art jobs, /art view, /art all, and /art getstatus is off by the server's UTC offset. Worse, in handleFinish (lines 635-637) `daysToComplete = Math.floor((Date.now() - assignedAt)/86400000)` can be off by a day, and for a job assigned minutes ago on a host with a positive UTC offset, `assignedAt` (parsed as local) can be GREATER than Date.now(), making the difference negative and rendering '... Completed in -1 days'. The repo already has the correct fix applied in src/ui/reviewCard.ts:110 and src/features/review/card.ts:129 (`trimmed.replace(' ', 'T') + 'Z'`), so this column format is known to need normalization before `new Date()`.

**Location:** `src/commands/art.ts:425, 635-637, 712, 732, 865, 1038`
**Category:** correctness | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Normalize the SQLite datetime string to ISO-UTC before constructing a Date, e.g. a helper `const ms = new Date(job.assigned_at.replace(' ', 'T') + 'Z').getTime();` reused at every call site (mirroring reviewCard.ts:110). Also clamp daysToComplete with `Math.max(0, ...)` to avoid negative day counts from clock/parse skew.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0031. See audit/2026-05-31/full-codebase-audit.md.
