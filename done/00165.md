# #00165 -- reopenModmailThread can throw on partial unique index when user already has a newer open ticket

**Type:** bug | **Priority:** Low

reopenModmailThread (userId path) selects the most recent ticket WHERE status='closed' (lines 46-56), then reopenTicket(ticket.id) runs `UPDATE modmail_ticket SET status='open' ...` (tickets.ts:174-179) with no guard against an existing open ticket for the same (guild_id, user_id). The runtime schema defines a partial unique index `idx_modmail_open_unique ON modmail_ticket(guild_id, user_id, status) WHERE status='open'` (src/db/db.ts:193-199). If the user already has an open ticket (e.g. a fresh thread was created after the prior one closed, or via the >7-day branch at threadReopen.ts:77-85 which opens a new ticket), flipping the old closed ticket back to 'open' violates the index and throws SQLITE_CONSTRAINT_UNIQUE inside the transaction (lines 89-109). The catch returns a generic 'Failed to reopen modmail thread' with no explanation. Integrity is preserved by the constraint, but the operation fails confusingly and the DM/unarchive side effects never run.

**Location:** `src/features/modmail/threadReopen.ts:46-109`
**Category:** data-integrity | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Before reopening, check for an existing open ticket for (guildId, userId) and either refuse with a clear message ('User already has an open modmail thread: <#...>') or close/merge it first. Alternatively wrap reopenTicket in a guard that detects the constraint and surfaces a specific message.
