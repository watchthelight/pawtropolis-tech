# #00081 -- redeemreward confirm button has no reentrancy guard: double-click duplicates art jobs and double-rotates the a

**Type:** bug | **Priority:** High

handleConfirm() runs the assignment side effects with NO idempotency/lock and only clears the buttons at the very end (interaction.editReply({components:[]}) at lines 282-285). The flow is: deferUpdate -> (await) remove ticket role -> (await) grant artist access / post `$add` -> processAssignment() -> createJob() -> logAssignment() -> editReply(clear buttons). Because the confirmation is a NON-ephemeral reply (src/commands/redeemreward.ts:294-297, no MessageFlags.Ephemeral) and handleConfirm never verifies the clicker is the invoker, the live button can be clicked twice in quick succession (or by two different staff) before the first invocation reaches the final editReply. Each click is a distinct Discord interaction with a distinct interaction.id, so the interactionCreate dedup map (src/events/interactionCreate.ts:69-97, which only de-dupes identical IDs from Discord network re-delivery) does NOT prevent it. The downstream operations are NOT idempotent: processAssignment (src/features/artistRotation/queue.ts:374-427) unconditionally rotates the artist to the end of the queue and increments assignments_count by 1 each call; createJob (src/features/artJobs/store.ts:114-161) always INSERTs a new art_job row with the next sequential job number. The random `confirmId` embedded in the customId is parsed but never recorded or consumed anywhere, so it provides no protection. Result of a double-fire: the artist is rotated twice (losing their fair queue position), assignments_count is over-counted, two art_job rows are created for one commission, two assignment_log rows, and for legacy Ticket Tool channels two `$add` commands are posted. This is a cross-file trust gap: the handler trusts that the queue/job stores enforce single-execution, but they only guarantee per-call atomicity, not idempotency. Note the codebase already solves this exact problem elsewhere (modmail threadOpen.ts uses a 'pending' PRIMARY-KEY lock row; byteTokenHandler.ts has explicit 'Step 3.5 race condition' cleanup and an initiator check), confirming this is an oversight rather than intentional.

**Location:** `src/features/artistRotation/handlers.ts:102-299`
**Category:** Concurrency / interaction reentrancy | **Confidence:** high | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** Guard the confirmation against re-entry before doing any work. Cheapest robust option: in handleConfirm, immediately after deferUpdate(), do an atomic 'consume' of the confirmation -- e.g. INSERT the confirmId into a small consumed_confirmations table (or art_job/assignment_log keyed by a UNIQUE confirmId) inside a transaction and bail if it already exists (ALREADY_PROCESSED), mirroring the review claimTx pattern. Alternatively, edit the message to remove the buttons (interaction.update / editReply with components:[]) as the FIRST action so a second click can't hit the live component, and add an initiator check like byteTokenHandler (reject if interaction.user.id !== the original invoker). Also make processAssignment + createJob run under a single guard so they cannot both execute twice.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0299. See audit/2026-05-31/full-codebase-audit.md.
