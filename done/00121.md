# #00121 -- reopenTicket can violate partial unique index when user has a newer open ticket

**Type:** bug | **Priority:** Medium

db.ts defines `CREATE UNIQUE INDEX idx_modmail_open_unique ON modmail_ticket(guild_id, user_id, status) WHERE status='open'` (db.ts:195-198), enforcing at most one open ticket per (guild,user). reopenModmailThread's user-based lookup (threadReopen.ts:44-57) explicitly selects the most recent ticket WHERE status='closed'. If, after that ticket was closed, a NEW modmail was opened for the same user (a normal sequence), that new ticket is already status='open'. reopenTicket() then runs `UPDATE ... SET status='open'` on the old closed ticket inside the db.transaction at threadReopen.ts:89-109, which collides with the partial unique index and throws SQLITE_CONSTRAINT. The transaction rolls back and the catch at threadReopen.ts:150-154 returns a generic 'Failed to reopen modmail thread. Check logs.' Impact: staff get an opaque failure (and a logged error/Sentry capture) instead of a clear 'user already has an open modmail' message; the real cause is hidden. The guard-table UPSERT in the same transaction would also have pointed the open_modmail row at the wrong (old) thread had the UPDATE succeeded.

**Location:** `src/features/modmail/tickets.ts:174-180`
**Category:** data-integrity | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Before reopening by userId, check for an existing open ticket (getOpenTicketByUser) and short-circuit with a clear message linking the existing thread; otherwise catch SQLITE_CONSTRAINT specifically in reopenModmailThread and surface 'This user already has an open modmail thread.'

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0165. See audit/2026-05-31/full-codebase-audit.md.
