# #00064 -- Byte token redemption is non-atomic: token role is removed before the multiplier is granted/tracked, so a mid-

**Type:** bug | **Priority:** Critical

handleConfirm performs a multi-step Discord+DB sequence with no transaction or rollback: Step 1 removes the token role (line 314-317), Step 3 adds the multiplier role (line 348-351), Step 4 writes the DB tracking row via upsertActiveMultiplier (line 385-394). These are independent awaited Discord REST calls plus a SQLite write. If the bot crashes, the process is killed, or roles.add() throws (rate-limit 429, transient 500, hierarchy change between the pre-flight canManageRole check at line 245 and the actual add) AFTER the token role has already been removed at line 314, the user has permanently lost their byte token (the giveaway/shop entitlement) and received no multiplier. The catch block at line 449 only edits the reply with a generic error; it does NOT re-add the removed token role. Because the token role IS the entitlement (there is no separate balance ledger - see usebyte.ts findMemberByteTokens which reads role presence as the source of truth), this is an irreversible economic loss. Cross-file: usebyte.ts treats role presence as the wallet, while byteTokenHandler.ts mutates that wallet non-transactionally and trusts that every step after the destructive remove() will succeed.

**Location:** `src/features/byteTokenHandler.ts:268-394`
**Category:** economy/atomicity | **Confidence:** high | **Audit severity:** critical (adversarially confirmed)

**Suggested fix:** Reorder to grant-then-consume (add multiplier + write DB row FIRST, remove token role LAST), so a failure leaves the user still holding the token. Alternatively, on any failure after the token removal, compensate by re-adding the token role in the catch block. Best: record an intent/ledger row before touching Discord and reconcile on restart.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0315. See audit/2026-05-31/full-codebase-audit.md.
