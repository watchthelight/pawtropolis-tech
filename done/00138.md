# #00138 -- Router error-card fallback uses ensureDeferred (ephemeral deferReply) + editReply, clobbering the source messa

**Type:** bug | **Priority:** Medium

The catch-all safety net calls ensureDeferred(interaction) then postErrorCard(...). ensureDeferred (cmdWrap.ts:437-474) only ever does deferReply({Ephemeral}); it never handles component interactions via deferUpdate. For a button/select that threw BEFORE acknowledging itself, ensureDeferred issues a deferReply (valid), so postErrorCard's editReply targets the ephemeral reply - OK. But for a button handler that already called deferUpdate() and then threw (e.g. redeemreward confirm in features/artistRotation/handlers.ts:120 onward, byteToken confirm), ensureDeferred sees deferred=true and returns, then postErrorCard -> replyOrEdit -> editReply edits the ORIGINAL component message, overwriting the confirmation/panel embed with the public error card. Note buttons are routed directly (not through wrapCommand), so their post-defer throws land here. The 'public so staff can see' comment in errorCard.ts:224-227 is also wrong on the common path where the prior defer was ephemeral.

**Location:** `src/events/interactionCreate.ts:1103-1119`
**Category:** correctness | **Confidence:** medium | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Make the router fallback component-aware: if interaction.isMessageComponent() and not yet acknowledged, deferUpdate() (or just followUp) rather than deferReply; and deliver the error card via followUp({ flags: Ephemeral }) when the interaction was acknowledged with deferUpdate, instead of editReply over the source message.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0269. See audit/2026-05-31/full-codebase-audit.md.
