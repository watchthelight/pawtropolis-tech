# #00125 -- Synchronous DB throw escapes Promise.allSettled, defeating the partial-results design

**Type:** bug | **Priority:** Medium

executeAnalyticsCommand builds the Promise.allSettled input by EAGERLY calling the query functions: `Promise.resolve(getActionCountsByMod(...))`, `Promise.resolve(getTopReasons(...))`, etc. The real query functions in src/features/analytics/queries.ts are synchronous (better-sqlite3) and re-throw on any DB error (queries.ts:144, 258, 357, 457, 527). Because the call happens during array-literal construction, a synchronous throw propagates out BEFORE Promise.allSettled is ever invoked, so it is NOT captured as a 'rejected' settlement. It is instead caught by the outer try/catch at command.ts:336, which logs an error and replies '❌ Analytics query failed' - the exact opposite of the intended behavior, which is to show partial results (warn + show whatever succeeded). One failing query thus blanks the entire command instead of degrading gracefully. The test tests/features/analytics/command.test.ts:271-283 ('handles query failures gracefully') hides this because it uses mockGetActionCountsByMod.mockRejectedValue(...) which returns an already-rejected Promise (async) rather than throwing synchronously like the real code path; so the test exercises a code path that production never takes.

**Location:** `src/features/analytics/command.ts:165-182`
**Category:** correctness | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Wrap each call so a synchronous throw becomes a rejected promise that allSettled can capture, e.g. use `Promise.resolve().then(() => getActionCountsByMod(...))` for each entry, or wrap the bodies in async helper functions. Then allSettled will correctly mark individual failures as rejected and the partial-results/warn path will run.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0184. See audit/2026-05-31/full-codebase-audit.md.
