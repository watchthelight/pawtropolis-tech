# #00076 -- Byte token double-click TOCTOU: entitlement gated only by eventually-consistent Discord role cache; concurrent

**Type:** bug | **Priority:** High

The sole entitlement check before redeeming is guildMember.roles.cache.has(tokenConfig.tokenRoleId) at line 283. The confirm button is never disabled and the ephemeral message's components are not cleared until the final editReply, so a user can fire two ButtonInteractions on the same button. interactionCreate routes each to a separate concurrent handleUseByteButton invocation (events/interactionCreate.ts:616-629); discord.js does NOT serialize interactions for a user. Both invocations deferUpdate, both fetch the member, both observe the token role still present (it is only removed at line 314, after several awaited REST calls), and both proceed. The CHANGELOG (line 322) and the Step-3.5 cleanup (lines 357-382) only address stacking of DISTINCT multiplier roles - and that cleanup explicitly excludes the role just added (roleId !== tokenConfig.multiplierRoleId at 361), so two same-rarity redemptions both add the same role (idempotent) and both reach upsertActiveMultiplier. The upsert's ON CONFLICT (byteMultiplierStore.ts:66-79) overwrites expires_at with a brand-new full-duration value every time, so the second click silently refreshes/extends the multiplier window for a single token. There is no atomic DB claim of the token. Worse, for the epic/legendary pair that share multiplier role 1405369052829974543 (usebyte.ts:87,96), holding both tokens and redeeming epic then legendary extends the same role's expiry to the longer 72h with the de-stack logic seeing nothing to remove.

**Location:** `src/features/byteTokenHandler.ts:267-394`
**Category:** race | **Confidence:** high | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** Gate redemption on an atomic DB claim, not Discord role state. Before any role mutation, run an INSERT OR IGNORE / UPDATE...WHERE into a per-token redemption ledger keyed by (guild_id, user_id, token_rarity) (or a UNIQUE claim row) and bail if changes===0. Additionally disable the confirm button immediately (interaction.update components disabled) at the very start of handleConfirm before deferring, and key the confirmId so a replayed click is rejected. Make the ON CONFLICT path additive/longest-wins on expires_at rather than blindly overwriting, so a stray second write can't silently shorten or refresh a window.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0262. See audit/2026-05-31/full-codebase-audit.md.
