# #00079 -- Review modal/button error handlers overwrite the review card with a public plaintext error after deferUpdate()

**Type:** bug | **Priority:** High

handleRejectModal (and handleAcceptModal:87-112, handlePermRejectModal:126-151, handleKickModal:165-190, handleVoteOutModal:203-228) all call interaction.deferUpdate() first, then on any thrown error call replyOrEdit(interaction, { content: 'Failed to process ... (trace: X).' }) with no flags. Via the cmdWrap.ts bug above, deferred=true routes this to editReply(), which edits the ORIGINAL review card message - replacing the applicant embed and action buttons with a bare public error string. The same defect exists in handleReviewButton's catch (buttons.ts:200-204) for the already-deferred actions (claim/wrong_password/stale_modmail) and in handleModmailButton's catch (buttons.ts:270-275). Net effect: a transient failure (DB hiccup, Discord 50013, etc.) during a moderation action not only fails the action but visibly destroys the review card for all staff, with the internal trace string leaked publicly into the staff channel.

**Location:** `src/features/review/handlers/modals.ts:49-74`
**Category:** correctness | **Confidence:** high | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** In these post-deferUpdate catch blocks, send the failure via interaction.followUp({ content, flags: MessageFlags.Ephemeral }) (the message component interaction still supports followUp after deferUpdate) instead of replyOrEdit/editReply, so the card is preserved and the error stays private to the acting mod.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0267. See audit/2026-05-31/full-codebase-audit.md.
