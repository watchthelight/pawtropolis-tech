# #00078 -- replyOrEdit silently drops the ephemeral flag and edits the source message after deferUpdate(), clobbering sha

**Type:** bug | **Priority:** High

replyOrEdit() decides between editReply/followUp/reply purely on interaction.deferred/replied, but discord.js sets deferred=true for BOTH deferReply() and deferUpdate(). The deferred branch (line 503-506) strips flags (`const { flags, ...editPayload } = withFlags`) and calls editReply(). After a component interaction has called deferUpdate(), editReply() edits the ORIGINAL message the component was attached to - it does NOT create an ephemeral reply. So every caller that does `deferUpdate()` then `replyOrEdit({ content, flags: MessageFlags.Ephemeral })` (1) loses ephemerality and (2) overwrites the source message. Concrete, routinely-triggered case: src/features/review/handlers/claimHandlers.ts handleClaimToggle - two mods click Claim at once; the loser hits ClaimError ALREADY_CLAIMED and calls replyOrEdit({content:'This application is already claimed by another moderator.', flags: Ephemeral}) (claimHandlers.ts:62-67). Because handleReviewButton already called deferUpdate() (buttons.ts:177-181), this becomes editReply on the review card: the embed, applicant info, and all action buttons are replaced with the bare public sentence, destroying the shared card for every mod. Same pattern: claimHandlers.ts:74,91,178,190,243 (the 'unclaimed successfully' / 'not owner' / perm-rejected messages all request Ephemeral and all instead wipe the card publicly).

**Location:** `src/lib/cmdWrap.ts:500-517`
**Category:** correctness | **Confidence:** high | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** Distinguish deferReply-state from deferUpdate-state. Track how the interaction was acknowledged (e.g., set a flag when deferUpdate is used, or check interaction.isMessageComponent() && deferred) and in that case send feedback via interaction.followUp({ ..., flags: MessageFlags.Ephemeral }) instead of editReply. Also stop discarding `flags` on the editReply branch when the intent is an ephemeral follow-up. At minimum, callers that did deferUpdate() should use followUp for ephemeral side-messages rather than replyOrEdit.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0266. See audit/2026-05-31/full-codebase-audit.md.
