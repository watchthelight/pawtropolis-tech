# #00098 -- Byte token confirm is a check-then-act race: entitlement is gated only on the eventually-consistent Discord ro

**Type:** bug | **Priority:** Medium

The only guard preventing double-redemption is guildMember.roles.cache.has(tokenConfig.tokenRoleId) at line 283, read from a member fetched per-interaction. The interaction-dedup in interactionCreate.ts (line 69-97, keyed on interaction.id) does NOT help here because two distinct clicks - or two confirmation messages produced by running /usebyte twice - carry distinct interaction IDs. There is no DB-level idempotency: upsertActiveMultiplier (byteMultiplierStore.ts line 66-79) uses ON CONFLICT(guild_id,user_id) DO UPDATE, which unconditionally rewrites expires_at to now+duration on every call. So a user who double-clicks Confirm can have both handlers pass the role.has() check before either removal propagates, and both call upsert; the second call resets the boost expiry to a fresh full duration off a single consumed token. The post-add race cleanup at line 353-382 only removes OTHER multiplier roles, not the duplicate grant of the same role, and does nothing about the duplicated expiry reset. There is no per-user lock around handleConfirm.

**Location:** `src/features/byteTokenHandler.ts:106-139, 268-394`
**Category:** economy/race | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Make consumption atomic in SQLite: gate redemption on a conditional write (e.g., an INSERT ... ON CONFLICT DO NOTHING into a redemption-claim table keyed by a single-use token instance, or a transaction that both records the spend and refuses if already spent) BEFORE removing the Discord role, and only proceed if changes===1. Add a short per-(guild,user) in-process mutex as defense in depth.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0316. See audit/2026-05-31/full-codebase-audit.md.
