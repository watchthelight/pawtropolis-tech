# #00214 -- 7-day reopen window parses SQLite UTC timestamp as local time

**Type:** bug | **Priority:** Low

closed_at is written by closeTicket() in tickets.ts via SQLite datetime('now'), which yields a space-separated UTC string like "2026-05-31 12:34:56" with no timezone marker (confirmed: db.ts line 187 `closed_at TEXT`, and closeTicket uses `datetime('now')`). At threadReopen.ts:73 this is parsed with `new Date(ticket.closed_at).getTime()`. Node/V8 parses non-ISO, space-separated datetime strings as LOCAL time, not UTC. The comparison `now - closedAt > sevenDays` (lines 74-77) is therefore skewed by the host's UTC offset. On a server several hours behind UTC, a freshly-closed ticket can compute a NEGATIVE elapsed time (closedAt appears in the future) and on a server ahead of UTC the window is shortened. Impact: the boundary between 'reopen in place' and 'create a brand-new thread' (lines 78-85) is off by the offset, so tickets near the 7-day edge are mis-routed. Not exploitable, but a genuine boundary/timezone bug.

**Location:** `src/features/modmail/threadReopen.ts:73-77`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Parse as UTC explicitly. Either store/read epoch seconds, or normalize: `const closedAt = ticket.closed_at ? new Date(ticket.closed_at.replace(' ', 'T') + 'Z').getTime() : 0;`. Best: make SQLite emit ISO-Z (e.g. strftime('%Y-%m-%dT%H:%M:%SZ','now')) or unixepoch() and parse consistently.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0164. See audit/2026-05-31/full-codebase-audit.md.
