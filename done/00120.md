# #00120 -- Gatekeeper-denial tests only assert the guard was *called*, never that the command aborted - an inverted/remov

**Type:** security | **Priority:** Medium

The 'denies access when user lacks gatekeeper role' test sets requireGatekeeper -> false and then asserts only `expect(requireGatekeeper).toHaveBeenCalled()`. It never asserts that the privileged work was skipped (e.g., that findAppByShortCode / approveTx were NOT invoked, or that no approval reply was produced). Because the denial message is produced inside requireGatekeeper itself (which is mocked away), the test has no observable post-condition for the abort. Consequence: if src/commands/gate/accept.ts regressed to `if (requireGatekeeper(...)) return;` (inverted) or dropped the early `return`, an unprivileged user could drive the approval flow and the suite would stay green. The identical weak pattern appears in the sibling gate-command tests, all on security-critical authz paths: gate/reject.test.ts (127-144), gate/kick.test.ts (137-146), gate/unclaim.test.ts (130-139), and gateMain.test.ts (202-209, requireStaff).

**Location:** `tests/commands/gate/accept.test.ts:129-146`
**Category:** security | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** After the guarded execute() call, also assert the command short-circuited: e.g. `expect(findAppByShortCode).not.toHaveBeenCalled();` and `expect(approveTx).not.toHaveBeenCalled();` (and the analogous tx/lookup mocks for reject/kick/unclaim/gate). This makes an inverted or removed guard fail the test.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0154. See audit/2026-05-31/full-codebase-audit.md.
