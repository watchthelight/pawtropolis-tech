# #00152 -- stamp-migrations version-to-name map is misaligned, so it marks the wrong (and unapplied) migrations as applie

**Type:** bug | **Priority:** Medium

stamp-migrations.mjs hardcodes a list mapping versions to names and inserts them into schema_migrations with ON CONFLICT DO NOTHING. The names are wrong: it maps '047' -> 'lock_db_mode', but the real migration is migrations/047_nsfw_reviewed_tracking.ts (verified on disk and via its exported migrate047NsfwReviewedTracking). There is no 047_lock_db_mode file at all. The list is effectively shifted/invented relative to the actual migrations directory. Because the migration runner (migrate.ts:253) decides what to skip purely by `version` membership in schema_migrations, stamping version '047' makes the runner skip the real 047 migration forever, even though its column changes (nsfw_flags.reviewed_by/reviewed_at) were never applied. The stored `name` being wrong also corrupts the audit trail. The same shift affects other entries (the names do not line up with the on-disk NNN_*.ts files). This is a footgun script that, if run on a fresh or partially-migrated DB, silently desyncs tracking from reality.

**Location:** `C:/Users/Claude-Code/pawtropolis-tech/scripts/stamp-migrations.mjs:4-26`
**Category:** deploy-safety/migration-tracking | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Generate the version/name pairs by scanning the migrations/ directory (same regex as migrate.ts: /^(\d{3})_(.+)\.ts$/) instead of a hand-maintained literal list, or delete the script. If a stamping tool must exist, have it import the scan from migrate.ts so it can never drift from the real filenames.
