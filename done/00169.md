# #00169 -- Recurring schedulers run on setInterval(async ...) with no re-entrancy guard - overlapping ticks duplicate wor

**Type:** bug | **Priority:** Low

Every scheduler uses `const i = setInterval(async () => { try { await work() } ... }, MS)` with no 'is a previous run still in flight?' flag (securityAuditScheduler.ts:349, guildSnapshotScheduler.ts:117, staleApplicationCheck.ts:393, modMetricsScheduler.ts:100, byteMultiplierScheduler.ts:210, diskSpaceScheduler.ts:247, eventTimeoutScheduler.ts:83). setInterval does not await the callback, so if one run's awaited work (Discord REST, guild.fetch(), generateAuditDocs which walks all roles/channels + saves a snapshot) exceeds the interval, the next tick starts a second concurrent run. For securityAudit this means two overlapping runs each call generateAuditDocs/saveSnapshot (src/store/securitySnapshotStore.ts:243) and each post to the logging channel with leadership pings (securityAuditScheduler.ts:195) - duplicate critical-alert pings and a diff computed against a snapshot the other run just wrote. guildSnapshotScheduler additionally mutates module state `_snapshotCount` (guildSnapshotScheduler.ts:94) non-atomically across overlapping async runs, perturbing the 'fetch online every 6th run' cadence. Lower-frequency than finding #1 but unbounded if any single run hangs on a slow API call.

**Location:** `src/scheduler/securityAuditScheduler.ts:338-362`
**Category:** race | **Confidence:** medium | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Add a module-level `let running = false` (or a shared promise) guard at the top of each interval callback: `if (running) { logger.warn('previous run still in flight, skipping'); return; } running = true; try { await work() } finally { running = false; }`. This is the standard fix and also fixes the _snapshotCount/_lastAlertTime ordering issues for free.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0253. See audit/2026-05-31/full-codebase-audit.md.
