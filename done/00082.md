# #00082 -- Migration 039 never records itself and runs on a different DB connection outside the runner transaction

**Type:** bug | **Priority:** High

Of all 70 migrations, 039 is the only one that (a) does NOT call recordMigration(...) and (b) imports the long-lived singleton `db` from ../src/db/db.js (line 12) instead of using the `db` argument the runner passes. The runner (scripts/migrate.ts:209-213) executes `db.transaction(() => migrateFn(db))` and itself NEVER inserts into schema_migrations -- recording is delegated entirely to each migration via recordMigration (see helpers.ts:149). Consequences: (1) Because 039 never writes a schema_migrations row, getAppliedVersions() never sees '039', so scanMigrations keeps it in `pendingMigrations` and it re-runs on EVERY `npm run migrate` / deploy. (2) migrateFn(db) ignores the passed handle; all of 039's writes go through the src/db/db.js singleton connection (a second connection to the same WAL file, opened with different pragmas and a prepare() wrapper). So 039's work happens OUTSIDE the runner's transaction -- if a later statement in that wrapped transaction threw, 039's index/renumber changes would NOT roll back, breaking the atomicity guarantee the runner advertises. The dedup + `DROP INDEX IF EXISTS` + `CREATE UNIQUE INDEX IF NOT EXISTS` body is itself idempotent so re-running is not catastrophic, but the migration is permanently 'pending', runs un-transactionally, and may touch a different DB path than the one the runner backed up.

**Location:** `migrations/039_fix_art_job_unique_constraint.ts:12-62`
**Category:** migrations integrity | **Confidence:** high | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** Change the signature to `export function migrate039FixArtJobUniqueConstraint(db: Database): void`, drop the `import { db } from "../src/db/db.js"` line so it uses the passed-in handle, and add `recordMigration(db, "039", "fix_art_job_unique_constraint")` at the end (importing it from ./lib/helpers.js), matching every other migration.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0309. See audit/2026-05-31/full-codebase-audit.md.
