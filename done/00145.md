# #00145 -- Observatory leaves / cumulative_net / cohort retention treat user_activity as a join/leave event log, but it s

**Type:** bug | **Priority:** Medium

rebuildDailyMetrics derives daily `leaves` from `COUNT(*) ... WHERE left_at IS NOT NULL GROUP BY date(left_at)` and `joins` from `date(joined_at)`, and cumulative_net accumulates joins-leaves. rebuildCohortRetention buckets members by join-week. But user_activity has PRIMARY KEY (guild_id, user_id) and is upserted: trackJoin (src/features/activityTracker.ts:40-48) does `ON CONFLICT(guild_id,user_id) DO UPDATE SET joined_at = excluded.joined_at, left_at = NULL`. So a member who leaves and later rejoins has their prior leave ERASED (left_at reset to NULL) and their original join day MOVED to the latest join. This makes historical daily `leaves` and `cumulative_net` change retroactively on every rejoin, undercounts gross churn, and shifts cohort membership/size for past weeks. The rollup faithfully reflects stored data, but it trusts user_activity to be an append-only event log when activityTracker maintains it as mutable current-state. (Same assumption underlies the pulse leave-spike / rapid-join-leave detectors in queries/pulse.ts.)

**Location:** `src/features/statsObservatory/refresh.ts:184-192, 295-326, 351-379`
**Category:** JOIN/source correctness (event-log assumption on a current-state table) | **Confidence:** medium | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Either source join/leave events from an append-only log (e.g. action_log member_join/member_leave events or invite_usage.joined_at_s) instead of user_activity, or explicitly document leaves/cohort as 'net current-state' metrics. If event-accurate churn is required, stop resetting left_at to NULL on rejoin and record each membership span separately.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0313. See audit/2026-05-31/full-codebase-audit.md.
