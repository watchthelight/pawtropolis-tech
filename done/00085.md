# #00085 -- Patreon art entitlements with quantity>1 collapse onto a single binary ticket role, so a tier promising 2 emoj

**Type:** bug | **Priority:** High

PATREON_ART_ENTITLEMENTS defines quantity>1 for some tiers (Legendary Fiona emoji: 2, line 38). handlePatreonArtRewards computes delta = entitlement - alreadyGranted (line 182) and then assigns the single ticket role exactly once (assignRole, line 189-195) regardless of delta, while upsertGrant sets quantity_granted to the full entitlement via MAX() (store.ts line 96-103). The DB high-water mark therefore records '2 emoji granted' but the user only ever holds ONE binary emoji ticket role. On the spend side (artistRotation/handlers.ts line 131-134) /redeemreward removes that one role, and because patreon_art_granted already reads 2 the periodic sweep (patreonRoleDedup.ts sweepOnce -> handlePatreonArtRewards every 10 min) sees entitlement(2) <= alreadyGranted(2) and never re-grants, so the second emoji ticket is silently lost. The grant ledger (quantity_granted) and the redeem mechanism (binary role presence) are two different representations that disagree whenever quantity>1. Note: a redemption-counter audit already on file (audit/2026-05-31) corroborates this; reported here as an independently-confirmed economy defect.

**Location:** `src/features/patreonArtRewards.ts:30-66, 89-103, 175-205`
**Category:** economy/correctness | **Confidence:** high | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** Track redeemed vs remaining (e.g., remaining = quantity_granted - redeemed) on patreon_art_granted, decrement remaining in the /redeemreward confirm handler, and re-grant the ticket role whenever remaining>0 and the user lacks it. Alternatively model quantity>1 as multiple distinct redeemable units. Until fixed, no tier should declare quantity>1 against a single binary ticket role.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0319. See audit/2026-05-31/full-codebase-audit.md.
