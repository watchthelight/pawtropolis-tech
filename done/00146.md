# #00146 -- Expiry cleanup deletes the DB tracking row before (and regardless of whether) the Discord multiplier role is r

**Type:** bug | **Priority:** Medium

removeExpiredMultipliers (byteMultiplierStore.ts line 182-204) fetches expired rows and DELETEs them in the same call. cleanupExpiredMultipliers then tries to strip the Discord role per entry. But if the guild is in panic mode the handler returns early at line 100-109 AFTER the row is already deleted (the code comment at line 105-107 acknowledges staff must remove the role manually). The same orphaning occurs on any non-thrown early return: guild not cached (line 90-97) or member fetch returning null (line 112-120). Because the authoritative record was already destroyed, the scheduler can never retry these, so an expired XP multiplier role persists indefinitely on the member - a continuing economic over-grant (free boost) that no automated process will reclaim. Cross-file: the store's 'delete-on-read' design (intended to prevent double-processing) trades away the ability of the scheduler to recover from its own skipped work.

**Location:** `src/scheduler/byteMultiplierScheduler.ts:99-109, 35-79`
**Category:** economy/correctness | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Only delete rows that were actually reconciled. Either (a) select expired rows, attempt role removal, and DELETE only the successfully-processed ids; or (b) keep the row and mark a processed/last_attempt column, deleting only after confirmed Discord removal. Skip-and-retain on panic mode / fetch failure so the next run can finish the job.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0320. See audit/2026-05-31/full-codebase-audit.md.
