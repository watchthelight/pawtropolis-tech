# #00289 -- Service keys set from Discord

**Type:** feat | **Priority:** High

Owner decisions 1 and 16 (#00287): the keys of the outside services are to be settable from Discord, so they no longer have to be put into the host's `.env` by hand. In the owner's words: "Make a way for this key to be configured discord-side".

Covers the Google Vision key (avatar scan, `/audit nsfw` and the web detection of #00290), the SauceNAO key, and the e621 account name and key.

What was built:

- `/service-keys`, owner only, with `status`, `set`, `clear` and `test`. The owner list is checked in the command and again when the form is submitted. Every answer is ephemeral.
- `set` opens a form, so the key is never part of the command text. The key is tried against its service in one real request and stored only when the service accepts it. A refused key changes nothing, and the answer shows what the service said.
- `status` says which service has a key and what is lost without one. It never shows a value. For Google Vision it also says when the scans are paused after a refusal.
- `test` tries the stored keys again, for example after billing was switched on.
- No key appears in a reply, a log line or an error message. The router's verbose payload log leaves key forms out.

Where the keys are stored, and why not in the database:

The first plan was an encrypted column in the database, with the environment as the fallback. The key for that encryption would itself have had to sit in the host's `.env`, so the secret would have depended on that file anyway and gained a second place to lose. The keys now go where every other secret of the bot already is: the `.env` file on the host. `deploy.sh` never ships or replaces it, and it is not part of the database backups. The dashboard is started with the same file, as it always was, so it can read nothing it could not read before. `src/lib/envFile.ts` replaces one line and renames a finished temporary file over the old one, so a crash cannot leave half a file.

The keys are read from the environment on every use, so a key counts from the next scan or lookup on, with no restart. There is one place a key can be, so nothing has to say which source won.

Who set a key and when is in the bot log (`service_key_set`, `service_key_cleared`), not in the status view.

Not covered: the Claude API key stays in `.env`, and the `/isitreal` keys keep their own setup in `/config isitreal`.

Could not be checked: the accepted path of the SauceNAO and e621 tests, because no account exists yet. Their refusals and the Google Vision refusal were checked against the live services.

Setting the Vision key this way does not change what Google answers today. That is HTTP 403 with one of two sentences, "This API method requires billing to be enabled" or "Permission denied on the service", both seen in the bot log between 2026-11-14 and 2026-11-15. The Google Cloud project behind the key needs billing switched on and the Cloud Vision API enabled. `/service-keys test` shows Google's answer once that is done.

Shipped in 26.1.0 (`58d6baca`) and live since 2026-11-15: Discord lists `/service-keys` for the guild. Its first run as a real interaction is the owner's.
