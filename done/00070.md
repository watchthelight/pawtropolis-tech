# #00070 -- Reopen within 7 days of a DELETED thread commits open-state then throws, leaving an orphaned 'open' ticket poi

**Type:** bug | **Priority:** High

On close, the default config modmail_delete_on_close (treated as true unless explicitly false in threadClose.ts:365 and :546) DELETES the Discord thread. reopenModmailThread first commits a transaction that flips the ticket to status='open' and re-inserts the open_modmail guard row (lines 89-109), then calls addOpenThread(ticket.thread_id) restoring the in-memory routing set (lines 113-116), and ONLY THEN does `interaction.client.channels.fetch(ticket.thread_id)` (line 120). For a thread that was deleted on close, that fetch rejects with Unknown Channel (10003), which is caught by the outer try/catch (line 150) and returns {success:false}. But the DB transaction and addOpenThread have already taken effect. Result: the ticket is now marked 'open' with a thread_id that no longer exists, the open_modmail guard row blocks the user from ever getting a NEW modmail (openPublicModmailThreadFor short-circuits on the existing guard row), and OPEN_MODMAIL_THREADS/handleInboundDmForModmail will route the applicant's DMs to a dead thread (silently failing). Because delete-on-close is the default, virtually every recently-closed ticket has a deleted thread, so the common `/modmail reopen user:@x` path (closed_at within 7 days -> reopen branch, lines 72-85) reliably lands in this broken state. The staff member is told 'Failed to reopen' while the system is left inconsistent.

**Location:** `src/features/modmail/threadReopen.ts:87-127`
**Category:** data-integrity | **Confidence:** high | **Audit severity:** high (adversarially confirmed)

**Suggested fix:** Fetch and unarchive/unlock the thread BEFORE mutating the DB and in-memory set, and treat a missing/deleted thread explicitly: if the thread can't be fetched (null or fetch throws), do NOT reopen in place - instead fall through to creating a fresh thread via openPublicModmailThreadFor (as the >7-day branch already does). Alternatively, wrap the unarchive in its own try/catch and roll back (reopenTicket->close, delete the open_modmail row, removeOpenThread) if the thread is gone. Either way, never leave status='open' with a thread_id that fails to resolve.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0088. See audit/2026-05-31/full-codebase-audit.md.
