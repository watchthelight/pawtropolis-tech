# #00193 -- Permission-filtered command list is cached without keying on member-fetch success/roles, so a transient member

**Type:** bug | **Priority:** Low

filterCommandsByPermission caches the filtered result under key `${guildId}:${userId}` only. The actual permission computation depends on the `member` argument (its roles), which is NOT part of the cache key. In both callers (autocomplete.ts:50-60 and index.ts:88-94 / handleHelpButton index.ts:316-323 / handleHelpSelectMenu index.ts:394-401 / handleHelpModal index.ts:458-465) the GuildMember is fetched with `.catch(() => null)`. If that fetch transiently fails, `member` is null, and for any non-owner hasPermissionLevel() returns true only for 'public' commands. That degraded public-only list is then written to PERMISSION_CACHE (line 283). For the next 5 minutes (TTL) the same staff/reviewer/admin user is served the public-only list from cache even when subsequent fetches succeed, because the cache hit (line 267-273) short-circuits before member is consulted. Net effect: staff intermittently see /help and /help autocomplete with only public commands. Self-heals after TTL. Display-only (does not affect command execution, which is independently gated), hence low severity.

**Location:** `src/commands/help/cache.ts:260-289`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Either (a) skip caching when `member` is null (the unreliable case), e.g. `if (member || isOwner(userId)) PERMISSION_CACHE.set(...)`, or (b) incorporate a role fingerprint into the cache key (e.g. a hash of sorted role IDs) so a different role set / null-member computes a distinct entry. Option (a) is the minimal fix.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0048. See audit/2026-05-31/full-codebase-audit.md.
