# #00227 -- Test encodes a fabricated INVALID_STATUS string and masks a real garbled-message bug for panic mode

**Type:** bug | **Priority:** Low

The test 'extracts status from error message' uses errorMessage = "Cannot claim: status is approved" and asserts split(" ")[2] === "status". This is not the real message and the asserted value ("status") is meaningless. The production handler (src/features/review/handlers/claimHandlers.ts:49-50) does `msg = `Cannot claim: application is already **${err.message.split(" ")[2]}**.`` against the ClaimError thrown by claimTx. claimTx throws INVALID_STATUS in TWO shapes: (a) terminal state -> "Application already approved" where split[2] = "approved" (correct), and (b) PANIC MODE -> "Panic mode is active. All review operations are suspended." (src/features/reviewActions.ts:62) where split[2] = "is". So when a moderator clicks Claim during panic mode they get the nonsensical reply "Cannot claim: application is already **is**." instead of a panic-mode explanation. The vacuous test neither reflects the real message nor catches the panic-mode garble.

**Location:** `tests/features/review/handlers/claimHandlers.test.ts:80-85`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** In claimHandlers.ts, branch on the actual ClaimError content instead of positional word parsing: surface err.message directly for the panic case (it is already user-friendly), and only do the 'already <status>' phrasing for the terminal-state case (e.g. detect a leading 'Application already '). Then write a real test that calls handleClaimToggle with claimTx mocked to throw both ClaimError shapes and asserts the rendered reply.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0203. See audit/2026-05-31/full-codebase-audit.md.
