# #00229 -- withTimeout never clears its setTimeout, leaking a 30s timer per DM (also in kick.ts)

**Type:** bug | **Priority:** Low

withTimeout races the work promise against `new Promise((_,reject)=>setTimeout(...,30000))` but never captures the timer handle, so it is never cleared. When user.send() resolves first (the normal case, exercised by reject.test.ts), the 30s timer stays pending until it fires and rejects an already-settled promise (no-op). Same pattern in src/features/review/flows/kick.ts:29-36 for fetch/send/kick - up to three dangling 30s timers per kick. Production impact is modest (timers are short-lived and self-clear) but it keeps the event loop active and, under bursts of approvals/rejections, accumulates thousands of pending timers; in tests it leaves real timers alive after the test ends since the suite uses no fake timers. Grep confirmed there is no clearTimeout anywhere in src/features/review/flows.

**Location:** `src/features/review/flows/reject.ts:26-33, 130-137`
**Category:** leak | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Capture the handle and clear it in a finally: `let t; const timeout = new Promise<T>((_,rej)=>{t=setTimeout(()=>rej(new Error(...)),ms);}); try { return await Promise.race([promise, timeout]); } finally { clearTimeout(t); }`. Apply in both reject.ts and kick.ts.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0211. See audit/2026-05-31/full-codebase-audit.md.
