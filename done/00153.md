# #00153 -- run-migration-046 tracks via a different table (migration_log) than the canonical runner (schema_migrations)

**Type:** bug | **Priority:** Medium

run-migration-046.mjs records its completion into a `migration_log` table (lines 24-27), but the canonical runner migrate.ts and migrations/lib/helpers.ts track exclusively in `schema_migrations` (migrate.ts uses schema_migrations 8x, migration_log 0x; migration 046 itself is 046_extend_user_cache_profile.ts and calls recordMigration into schema_migrations). Consequences: (a) running this ad-hoc script does NOT mark 046 as applied in schema_migrations, so the next `./deploy.sh` will re-run migration 046 via migrate.ts; (b) it ALSO opens the DB with `new Database(dbPath)` defaulting fileMustExist:false and DB_PATH defaulting to './data/data.db' relative to cwd, so if invoked from the wrong directory it creates an empty DB and ALTERs a non-existent user_cache; (c) the `SELECT id FROM migration_log` will throw if migration_log does not exist on a given box, since nothing in the canonical schema creates it. The additive ALTERs are individually guarded by a column-existence check so re-running 046 via migrate.ts won't duplicate columns, which is the only reason this is medium and not high, but the dual-table tracking is a real inconsistency that breaks the 'applied versions' contract the whole deploy relies on.

**Location:** `C:/Users/Claude-Code/pawtropolis-tech/scripts/run-migration-046.mjs:1-32`
**Category:** deploy-safety/migration-tracking | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** Delete run-migration-046.mjs (migration 046 is already covered by migrations/046_extend_user_cache_profile.ts run through migrate.ts). If kept for emergencies, have it write to schema_migrations via the same recordMigration helper, require fileMustExist:true, and resolve DB_PATH the same way migrate.ts does.
