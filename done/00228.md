# #00228 -- Local BUTTON_RE copy diverges from the real BTN_DECIDE_RE, so routing-regex tests prove nothing

**Type:** bug | **Priority:** Low

The suite defines its own `const BUTTON_RE = /^v1:decide:(\w+):code([0-9A-F]{6})$/` and tests claim/unclaim/approve/etc. against it. The actual pattern used by handlers (src/lib/modalPatterns.ts:35, re-exported as BUTTON_RE from helpers.ts:38) is `/^(?:v1:decide|review):(approve|accept|reject|kick|claim|unclaim|wrong_password|stale_modmail):code([0-9A-F]{6})$/`. Two concrete divergences: (1) the real regex also accepts the legacy `review:` prefix, which the test's copy rejects; (2) the real regex constrains the action to a fixed allowlist whereas the test copy accepts ANY `\w+` (so `v1:decide:garbage:codeABCDEF` would 'match' in the test but not in production). The tests therefore validate a fictional regex; a change to the real allowlist or prefix handling would not be caught.

**Location:** `tests/features/review/handlers/helpers.test.ts:191-258`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Import the real BUTTON_RE/MODAL_RE/ACCEPT_MODAL_RE from src/features/review/handlers/helpers.js (or BTN_DECIDE_RE etc. from src/lib/modalPatterns.js) instead of re-declaring local literals, then run the same match assertions plus a `review:`-prefixed case and an invalid-action negative case.
