# #00158 -- Permission cache is never invalidated on role change (invalidatePermissionCache is dead-wired)

**Type:** bug | **Priority:** Low

filterCommandsByPermission caches the visible-command list under key `${guildId}:${userId}` with a 5-minute TTL (PERMISSION_CACHE, line 208). The only invalidation path is invalidatePermissionCache (line 325), but a repo-wide search shows it is never called from any production module (only its own file, tests, and graphify artifacts). Consequence: when a member's roles change (promotion to staff/reviewer, or demotion), their /help output stays stale for up to 5 minutes. This is not merely cosmetic: showCommandDetail (index.ts:220-235) reuses filterCommandsByPermission as an authorization gate and replies "You don't have permission to view /<cmd>" for any command not in the cached list. So a just-promoted staffer is falsely told they cannot view staff command help, and a just-demoted user can still read help for commands they lost - until the TTL expires. The code's own comment (lines 206-207) promises this invalidation happens; it does not.

**Location:** `src/commands/help/cache.ts:260-289, 325-327`
**Category:** correctness | **Confidence:** high | **Audit severity:** low (adversarially confirmed)

**Suggested fix:** Call invalidatePermissionCache(guildId, userId) from the role-change paths (e.g., roleAutomation / guildMemberUpdate handlers), or key the cache on a hash of the member's role IDs so role changes naturally miss the cache. At minimum, shorten the TTL or expose a bulk clear hook that role-update events invoke.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0044. See audit/2026-05-31/full-codebase-audit.md.
