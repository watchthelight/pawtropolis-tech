# #00112 -- Already-resolved/terminal/invalid guard replies overwrite the review card embed after deferUpdate

**Type:** bug | **Priority:** Medium

All of the run*Action functions are reached after the interaction has already been acknowledged with interaction.deferUpdate() (every modal handler in modals.ts calls deferUpdate before invoking the runner, and the wrong_password/stale_modmail button paths in buttons.ts:96-141 also deferUpdate before calling runRejectAction). After deferUpdate, discord.js sets interaction.deferred = true (verified in node_modules/discord.js InteractionResponses.deferUpdate, and the deferUpdate doc explicitly says it defers an update to 'the message to which the component was attached'). lib/cmdWrap.replyOrEdit then takes the `interaction.deferred` branch and calls interaction.editReply(), which edits the SOURCE review-card message. So when two moderators race (e.g. one approves, the other clicks reject/kick/approve a moment later), the loser's guard branch (`replyOrEdit(interaction, { content: 'Already approved.' })` / 'This application is already resolved.' / 'Already resolved (...)' / 'Application not ready' etc.) replaces the entire review card's embed + buttons with a bare plain-text line. The card is only repaired later if some other path happens to call ensureReviewMessage; on these early-return guard branches it is not refreshed, so the card stays clobbered. Note the modal-opener guards in helpers.ts correctly pass flags: MessageFlags.Ephemeral and run before showModal (interaction not yet acked) so they reply ephemerally and are fine - the defect is specifically the post-deferUpdate runners which omit the ephemeral flag.

**Location:** `src/features/review/handlers/actionRunners.ts:84-101, 297-339, 460-502, 657-674, 783-788, 821-826, 939-946`
**Category:** discord-api-misuse | **Confidence:** high | **Audit severity:** medium (adversarially confirmed)

**Suggested fix:** On the early guard branches inside the run*Action functions (and the duplicate-resolution checks in runVoteOutAction), do not use editReply on a component-deferred interaction. Either pass flags: MessageFlags.Ephemeral and use interaction.followUp(...) for the notice (followUp is valid after deferUpdate and posts an ephemeral message instead of editing the card), or refresh the card via ensureReviewMessage and send the notice as an ephemeral followUp. Concretely, replace replyOrEdit(interaction, { content: ... }) with interaction.followUp({ content: ..., flags: MessageFlags.Ephemeral }).catch(...) in these guard paths.

**Evidence:** full-codebase multi-agent audit 2026-05-31, finding A0100. See audit/2026-05-31/full-codebase-audit.md.
